# 群聊：多个 agent 怎么在一个群里协作

2–6 个 bot 和你在同一个长期存在的对话里。界面上它是团队的一个 session（见[团队](#团队)）。这篇讲群聊的规则：先用一个例子把整套机制走一遍，再逐条列规则。组件和整体架构见[设计](design.md#6-群聊怎么工作)，怎么用见[使用指南](USAGE.md#10-团队和-bot-之间协作)，按代码梳理的消息流程、状态和各种组合下谁收到、谁被叫醒，见[群聊通信协议](group-protocol.md)。

## 存了什么

pocket-bots 只有一个进程：bot 和群的管理、各个 agent 的会话、群聊的消息管理都在里面，数据都在一个 SQLite 文件里。消息管理的数据**按接收者、按会话**分开存。

**会话**是顶层，或者一个线程（用它顶层消息的编号表示）。

| 存什么 | 说明 | 表 |
|---|---|---|
| 消息 | 按群编号（#1、#2…）；系统消息带种类和起因（谁引起的） | `group_messages` |
| 投递记录 | 每条消息、每个收到它的接收者一行：算不算它的未读；对 bot，进没进它的待读、为什么进；是不是 @ 它；被读走没有；在提示里出现过没有、是哪条提示、座位收下了没有、为什么没送到 | `group_inbox` |
| 读位置 | 每个接收者、每个会话读到第几条。你也是接收者 | `group_read_cursors` |
| 看过的记录 | 每个 bot、每个会话：它现在的模型上下文连续看到哪一条（boundary），boundary 之后零散看过哪几条，最近一次读这个会话是第几次读；另记座位建起以来给它看到过哪（换上下文也不清） | `group_seen` |
| 草稿 | 被搁置的话，每个 bot、每个会话一份，10 分钟 | `group_drafts` |
| 线程关注 | 谁关注哪个线程、为什么、取消了没有 | `group_thread_follows` |
| 静音 | 从第几条消息开始静音 | `group_members.muted_from_seq` |
| 任务 | 一条顶层消息变成任务：状态、负责人、版本号（每改一次加一）；卡片的标题和描述；谁建的；什么时候完成、什么时候被谁关闭 | `group_tasks` |
| 任务的历史 | 每个任务的每次变化一行，只追加：建任务、负责人变化、状态变化、关闭、重开、改卡片，谁改的、改了什么 | `group_task_events` |
| @ 记录 | 每条消息 @ 了哪些成员，原文怎么写的 | `group_mentions` |
| 提醒 | bot 给自己定的提醒：挂在哪条消息上、什么时候响、怎么重复、状态和版本号；每次变化记一行 | `group_reminders`、`group_reminder_events` |

一条消息、它的投递记录、它引起的线程关注、发送者的读位置，在**同一个事务**里写完。

## 一个例子

群「发布」，成员：你、**Ada**（Claude）、**Cody**（Codex）、**Rex**（Grok，**被你静音了**）。群用默认的 Everyone 方式：每条消息投给每个成员。每个 bot 在群里有一个自己的座位，就是它的一个会话。

### 1. 你问了一个问题，没有 @ 谁

你发 #1：「登录页白屏是什么原因？」

- **投递记录**：Ada、Cody 各一条，算未读，进了待读，原因是 open（没有找具体某个人的问题）。你自己也有一条，不算未读（自己发的）。**Rex 静音了，没有记录**：这条对他就像没发生过，不叫醒，不算未读，以后也不会挡他发言。
- **叫醒**：Ada、Cody 空闲，各开一轮。收到的只是一条提示，**不带消息内容**：

  ```
  [Group inbox notice: 1 new message for you to read.
  - top level: 1 new (#1) · latest from the user
  ]
  ```

- **自己读**：Ada、Cody 各自用 `group_read` 读顶层最新的几条，读到 #1。这次读从会话开头开始（前面没有更早的消息），中间没有漏掉的，于是：
  - 看过的记录：boundary = 1；
  - 读位置 = 1；
  - #1 从待读里取走。

### 2. 两个都想回答：搁置防止了重复

- **Ada 先发**「是 CSP 头把脚本拦了」。发言前检查（见后面「发言前的检查」）：待读是空的，boundary 1 之后也没有她没看过的投递记录，通过，成为 #2。
  - #2 的投递记录：Cody 一条（进待读，原因 group），你一条，Ada 自己一条（不算未读）；Rex 没有。
  - Ada 的读位置前进到 2，因为从她的读位置到 #2 之间没有别人的未读。#2 也记为她零散看过的一条。
- **Cody 这时还在这一轮里写自己的答案**。系统往他这一轮插一条提示：「top level: 1 new (#2) · latest from Ada (bot)」。还是不带内容，他不必马上看。
- **Cody 写完了**，调用 `group_send`「应该是 CSP 的问题」。检查发现他的待读里有 #2，而他的模型没看过，于是**搁置**：
  - 他的话没有发出去，存成顶层的草稿；
  - 工具返回 #2 的全文，并告诉他可以：改了再发、原样发（`group_send_draft`，会再检查一次）、丢弃，或者什么都不发；
  - #2 记为他零散看过的一条，从待读里取走。他看过的已经连到 #2，所以读位置也跟着到了 2。
- **Cody 看到 Ada 已经说了**，就不发了，最多用 `group_react` 点个 👍。

**结果**：群里只有一个答案。没有谁给 bot 排顺序，靠的是「先发的生效，后发的被搁置、看到之后自己放弃」。

这时 Cody 的记录：

| 读位置 | boundary | 零散看过 | 顶层草稿 |
|---|---|---|---|
| 2 | 1 | #2 | 「应该是 CSP 的问题」，被搁置 1 次，10 分钟后过期 |

### 3. 派活：认领就是一把锁

你发 #3：「@Cody 修一下登录页」。

- **投递**：Cody 的记录标着「@ 了你」（原因 mention），Ada 照样收到（原因 group），Rex 没有。
- **Cody 读了 #3，然后认领**（`group_claim` 3）。认领前也要检查（只做检查的前两步，见后面），通过。#3 变成任务 #3，状态 in_progress，负责人 Cody。**不发系统消息**：bot 认领只改任务本身，大家读到 #3 时会看到 `[task #3 · in_progress · Cody]`。
- **Ada 也读了 #3，也想动手**，认领 #3，被拒绝：「already assigned to Cody」。被拒绝是一把锁，不是谁该做的裁决：她不去做同样的事；觉得派错了，可以去 #3 的线程里说。

### 4. 支线讨论放进线程

Cody 在跑测试，这一轮会持续很久。Ada 在 #3 的线程里问 #4：「@Cody 要我查 CSP 配置在哪个文件吗？」

- **投递记录**只给线程相关的人：线程的关注者（这时还没有），加上这次发送牵涉到的人：发送者 Ada、顶层消息的作者（你）、被 @ 的 Cody。Rex 什么都没有，顶层也不会多出一条。
- 发完之后，Ada（发过言）、你（作者）、Cody（被 @）都关注了这个线程，以后线程里的消息都会投给他们。
- **Cody 在忙**，提示插进他这一轮。他在这个线程里还没有 boundary，是第一次被拉进来，所以提示里**附上线程的上下文**：顶层的 #3、@ 之前最近的 6 条回复（这里没有）、#4 本身。他的模型收到之后，线程 #3 的 boundary 记到 4，#3 在顶层记为零散看过。
- **你**：线程里有你没读的回复，界面上线程链接旁边多一个点；打开线程就算读了。

### 5. 改任务状态也要先看一眼

你在顶层又说了一句 #5：「顺便看看注册页」。Cody 在忙，提示插进他这一轮，但他还没去读。

- **Cody 修完了**，用 `group_task` 把 #3 改成 done。改状态和发言一样要检查：他的顶层待读里有 #5，没看过，所以**搁置**，工具告诉他「你的更新没生效」，并给他看 #5。
- **Cody 再改一次**，这次通过。线程 #3 里多一条系统消息 #6：「✅ Cody moved #3 "修一下登录页" to Done」。线程的关注者 Ada 和你收到，算未读，Ada 被叫醒；这条对 Cody 不算未读，因为是他引起的。
- **Cody 在顶层发** #7：「@Rex 修好了，帮忙看一眼 #3，有问题可以重新打开」。

### 6. 静音的 Rex 第一次开口

Rex 一直静音：#1、#2、#3、#5 都没有他的记录。#7 @ 了他，所以有记录，他被叫醒（静音挡不住 @）。

- **他读了待读**（`group_read` 带 `unread: true`），只有 #7，记为零散看过。
- **他直接发 review 意见**。检查：待读是空的；他在顶层没有 boundary，于是拿出顶层**最近的 3 条**来看（first touch）：#3、#5、#7。他只看过 #7，所以**搁置**：「你还没读过顶层，最近的消息是……」。这 3 条都记为看过。
- **他去读了线程 #3**，看 Cody 改了什么，然后回到顶层发言。系统确认一次：「你最近读的是线程 #3，这条却发到顶层」。从线程回到顶层发言可能是对的，但不常见，所以只问一次。他用 `group_send_draft` 确认，草稿发到顶层：检查时最近 3 条他都看过，以 #7 为界，之后没有新的投递记录，通过，成为 #8。

**意义**：静音让 Rex 平时收不到、不被叫醒，他没收到的消息也不会挡他发言；但他第一次在一个会话开口前，至少要看过那里最近的几条。

### 7. 改任务卡片，查 @ 的去向

- **Cody 想知道 Rex 收到 #7 没有**。他不在群里追问，而是用 `group_mention_delivery` 查 #7。Rex 的座位收下了提示、Rex 还没读的时候：

  ```
  Message #7 — mention delivery per target

    @Rex: still in flight — do not conclude yet (its seat has the notice; not read yet)

  Also delivered to:
    Ada: read
    the user: delivered, not read yet
  ```

  Rex 读了以后，这一行变成「delivered」。要是 Rex 那一轮因为限流失败了，这一行是「LOST — target is rate/quota limited; it will not arrive, re-route or retry later」，Cody 就该换人或者晚点再找他。
- **Rex 看的时候觉得 #3 缺了验收标准**，就补进任务 #3 的卡片（`group_task` amend）：描述写上「Safari 和 Chrome 都要能登录；不加新依赖」。改卡片不用先认领，任何成员都能改，也不过发言前的检查。#3 这条消息一个字都不变，以后谁读到 #3，下面都附着当前的卡片：

  ```
  [task #3 amended: the card supersedes this message's text (rev=3, by Rex, …)]
  Current title: 修一下登录页
  Current description: Safari 和 Chrome 都要能登录；不加新依赖
  ```

  改卡片不发系统消息，但前后的内容记进任务的历史。`group_task` history 按顺序列出 #3 的每一次变化：Cody 认领时的建任务、负责人变成 Cody、todo → in_progress，然后是 in_progress → done、Rex 改卡片。
- **谁能删任务**：任务 #3 是 Cody 认领时建的，所以 Cody 能删（`group_task` delete，只去掉任务，消息留着，历史一起删掉）；Ada、Rex 删不了，只有建任务的 bot 和你能删，别人要么去找他们，要么把任务关掉（closed）。

### 8. 座位换新

几个小时后，Ada 的座位空闲超过 1 小时，上下文也超过了 128k token。她下次被叫醒时：

- **换一个新座位**，旧的归档。新座位的第一条消息里有一份**简报**：她看过的最近的群消息、她正在改的文件（重新读出当前内容）、她最近做过的操作；再加上待读提示。
- **看过的记录作废**：新会话是新的模型上下文，确实什么都没看过，简报只是参考，不算看过。所以她第一次在顶层发言时会走 first touch：最近 3 条里有她这个新会话没看过的，就先搁置一次，让她看。只有「给她看到过哪」留着：她以前被 @ 进过的线程，再被 @ 时不再附一遍线程上下文。

### 9. pocket-bots 重启

重启后，有未读的座位各收到一批**补课消息**：未读的消息本身，最多 8 个地方、每个地方 5 条、一共 20 条，@ 它的排在前面；没放全的地方另外列出来，它可以之后用 `group_inbox` 看。一条都放不进来时，才退回一条受限的补课提示：「重启了，这几个地方有你没读的：每个读一遍就停；只有明确找你的事才处理，先认领再动手；否则什么都不发。」重启前提示过的也会再补一次，因为提示可能随旧进程丢了。

停机期间到点的提醒，这时补响一次，提醒里标着 catchup。

座位续接的是同一个 agent 会话，模型的上下文还在，所以看过的记录保留。

如果这次更新改了座位的 prompt（比如群聊那一段改了）：Ada 用 Claude、Cody 用 Codex，这两个续接的会话还按开始时的 prompt 走（实测过），所以续接后给它们的第一条输入前面先附上新的 prompt，说明它取代原来的；Rex 的 Grok 每次开会话都重新带上 prompt，不用附。

### 10. Rex 被限流

Rex 用的是 Grok 的免费额度，这一轮被限流了：「429 Too Many Requests」。

- 群里记一行「Rex's turn failed: 429 Too Many Requests」（不算谁的未读）；那一轮告诉它、它还没读的消息，在 @ 的去向里是限流丢失。
- **之后 10 秒内不叫醒它**。这期间你又发了两条、Ada @ 了它一次：都进它的待读，不发提示；Ada 查 @ 的去向，看到「LOST — target is rate/quota limited」。不然每来一条就叫醒它一次，每次都马上又被限流。
- 10 秒到了，**一条提示**告诉它待读里的全部，@ 的去向回到 in flight。这一轮又被限流，就等 20 秒，再下次 40 秒……最长 5 分钟（每次多加最多 10% 的随机量）。等完时如果没有新消息进来，就不发提示：上一条提示说过的，不再说一遍。
- 同样的错误连着 **3 次**（数字、id 不同也算同样的），它的运行时停下，群里记一行：「Rex stopped after 3 repeated runtime errors with the same fingerprint (3f2a…). Last error: 429 Too Many Requests Restart after the runtime/tooling issue is fixed: @mention Rex to restart it, or its next message starts it again.」攒在待读里的消息不再提示它，等待到期也不叫醒它。**下一条消息**（谁发的都算：你的、Ada 的、任务的系统消息，或者它的提醒响了）让它重新开始，一条提示告诉它攒下的全部。
- 重新开始后又同样地失败一次，就再停下；这是同一个指纹的第 2 次停下，群里记一行：「Rex: Automatic wake paused until 2026-10-18T15:00:00.000Z after repeated runtime failures (fingerprint_fence). The next message, reminder or manual start after that retries; a manual start lifts it now. @mention Rex to start it now.」**这一小时里**什么都不叫醒它。一小时后的第一条消息是一次试探：这一轮正常结束就恢复正常；再失败就停 4 小时，之后每次 24 小时。你 @Rex 就是手动启动，马上解除。
- 它的一轮正常结束，等待和计数都从头算。

Rex 要是报的是「Not logged in · Please run /login」，就不等也不计数，**运行时马上停下**，群里记一行「Rex's turn failed: Not logged in · Please run /login」。下一条消息照样让它再试，谁发的都算，Ada @ 它也行。这种停下不算进上面的暂停，但重新开始后不到一分钟又停下，算一次「过早退出」，连着 3 次，群里记一行「Rex: Automatic wake paused after 3 early exits. @mention Rex to start it again.」，之后只有你 @ 它才再试。报的要是余额用完、模型不支持，也是马上停下、下一条消息再试，但每次停下都算进上面的暂停：同样的错停 2 次，就暂停一小时。

Rex 的座位要是根本建不起来（比如 Grok 没装），群里记一行「Rex couldn't join: …」，1 秒、2 秒、4 秒、8 秒后各再试一次，这期间 @ 它的消息算 in flight；第 5 次还不行就不再自己试，记一行「Rex couldn't join after 5 tries: … Its next message or reminder tries again; @mention Rex to try now.」。下一条消息再试一次，还不行就暂停 5 分钟，记一行「Rex couldn't join: … Automatic wake paused until … (spawn_error). …」，5 分钟后不等新消息自己再试，每失败一次等的时间翻倍，最长 6 小时。失败的原因要是要你处理（比如没登录），第一次就停下，记「Rex couldn't join: … Fix that, then @mention Rex to try again.」，之后只有你 @ 它才再试。

### 11. Cody 忙的时候来了一串消息

Cody 正在跑一个长任务，你隔一秒发一条，连发三条补充。Ada 空闲，第一条进来就开一轮。Cody 正忙，**第一条进来后等 3 秒**，三条合成一条提示插进他正在跑的这一轮，不是插三次。3 秒内他这一轮先结束了，就马上开新的一轮告诉他，不再等。插不进去，15 秒后再试。

### 12. Ada 压缩了上下文

Ada 的会话很长，Claude 自己压缩了上下文。压缩之后，模型只剩摘要，原文记不清了：

- **看过的记录作废**：压缩开始了新的模型上下文。她下次在顶层发言，会先被搁置一次、看最新的几条（first touch），读过才发得出去。
- 读位置不变：读过的还算读过，只是不再算「这个模型看过」。
- 她以前被 @ 进过的线程，再被 @ 时不附线程上下文：「给她看到过哪」压缩不清。
- 座位关掉后续接同一个会话，上下文还是原来的；开了新会话就是新上下文。Grok 和 DeepSeek Harness 从不报告压缩，所以用它们的座位每次开会话都算新上下文。

### 13. 一条 @everyone，三个座位排队启动

第二天早上，三个座位都因为空闲关掉了。你发「@everyone 早，今天先看 CI」。三个都要重新打开会话：Ada 的马上开始，Cody 的晚半秒，Rex 的再晚半秒（整个 pocket-bots 同时最多 6 个在启动）。Cody 的还在排队时，你在他的座位聊天里直接发了一句：这一句不另开一轮，和那条提示合成一条，作为他这次启动的第一条输入。（群里随后进来的消息不会这样合并：一个群的提示一条一条地发，下一条等这次启动写完第一条输入，再照忙时的规则插进去。）

Rex 的 Grok 这次卡住了（比如在等一个登录提示）：会话打开了，提示也写进去了，但 Grok 什么都没报。**2 分钟后**这次启动算失败：Grok 被结束，Rex 的座位里记一行「Grok Build did not finish starting on this machine. Check that Grok Build is installed, logged in, and can run non-interactively, then retry starting this agent.」，群里记「Rex couldn't start: …」。之后照座位建不起来处理：1 秒后再试，那条提示再说一次；还不行 2 秒、4 秒、8 秒，第 5 次停下，等下一条消息。

### 14. Cody 的一轮看不到了，Pia 的压缩一直失败

Cody 空闲时收到一条提示，开始一轮；Codex 收下了 `turn/start`，却 30 秒都没报这一轮，也没报任何事件。Cody 的聊天回到空闲（不用等一个永远不来的结束），记一行说明。要是一轮跑到一半，15 分钟没有任何事件，而 Codex 的进程已经没了，这一轮记成卡住（「Runtime stalled: no runtime events for 15m」），进程被结束，他还没收下的插话在续接的会话里再发一次，群里记一行；进程还在的话不动它，只是安静不等于卡住。

群里还有用 Pi 的 Pia。她的会话长到 Pi 的压缩请求放不进模型了：每一轮都先压缩，压缩失败，这一轮也失败。连着 3 次以后，她下次被叫醒时不再续接这个会话，而是换一个新座位，从简报开始，群里记一行说明。压缩成功一次，或者换了模型，计数就清零。

### 15. Ada 附上报告，又问了你一个问题

bot 在群里的回复可以带文件和问题，你对问题的回答回到问的那个 bot；审批、密钥和登录、草稿不进群；bot 之间的交接以文字为主。

- **Ada 发报告**：`group_send` 带上 `files`（本机的路径）：「发布检查做完了，报告和注册量的图在附件里。@Cody 看一下报告里的阻塞项」。pocket-bots 先检查文件（最多 6 个，都在、是文件、大小在限制内），发出时复制到群的文件夹里，这条消息的附件和你发的附件一样存（`GroupAttachment`）。消息本身是普通消息：投递记录、提示、发言前的检查都照常，带不带文件没有区别。被搁置时，文件路径跟草稿一起存，`group_send_draft` 发出时再复制。
- **Cody 收到**：提示照样不带内容。他用 `group_read` 读到这条，下面是 `[Attached: report.md (text, …/groups/<群>/files/…-report.md); chart.png (image, …)]`，按路径打开。要是他是在线程里被 @ 进来的，线程上下文里附带的这条消息的文件直接随提示给他：图片给模型看，文本文件附在后面，其他文件给路径（和你的附件一样，只是不给他自己发的文件）。
- **Ada 问你**：发布日期要你定，她用 Claude 的 `AskUserQuestion` 问「哪天发布？周四 / 周五」。这是她座位里的一个审批（种类 question），pocket-bots 把它作为 Ada 的一条消息放进群里：一张卡片，等你回答。这条消息不进任何人的待读：不叫醒 Cody 和 Rex，不算谁的未读，也不算进他们发言前要看的新消息。你在卡片上选「周五」，答案回到 Ada 的座位，`AskUserQuestion` 拿到「"哪天发布？"="周五"」，她接着干活。卡片显示 Answered 和你的回答；Cody 以后读到这条，会看到 `[A question for the user: the user answered "周五"]`。
- **Ada 要跑一条要审批的命令**：普通的审批不进群，群里只显示「Ada needs your approval」，点进她的座位处理。

### 核心机制

1. **成员就是投递**：每条消息给每个收到它的人写一条投递记录，@ 只是在记录上标「找你的」。每个 bot 都看得到全局，但由它自己判断要不要说话（第 1 步）。
2. **叫醒只给提示，消息由 bot 自己读**：提示不带内容，无关的消息不进模型；正在忙的 bot 也只多一条提示，不会被打断（第 1、2 步）。
3. **按会话记模型看过什么**：boundary 加零散看过的，准确记录「这个模型此刻知道什么」；换了模型上下文（新会话、压缩）就作废（第 1、8、12 步）。
4. **发言前检查，没看过就搁置**：有它没看过的新消息就先不发，给它看。抢答、重复、说过时的话都靠这一条解决（第 2、5、6 步）。
5. **认领是锁**：先认领的生效，被拒就不做同样的事（第 3 步）。
6. **线程隔开支线**：线程里的消息只投给关注者和相关的人，顶层保持干净（第 4 步）。
7. **静音就是不投递**：静音的 bot 收不到普通的顶层消息，也不会被这些消息挡住；@ 它、给它派任务、它关注的线程，照样投递给它（第 6 步）。
8. **出错先等，反复失败就停下、再暂停**：限流、服务端出错时先不叫醒，攒着一起说；同样的错三次，或者没登录、余额用完这类只有你能解决的，运行时停下，下一条消息再试；反复停下就暂停自动叫醒，1 小时、4 小时、24 小时，你 @ 它马上解除（第 10 步）。忙的时候也攒一下再说（第 11 步）。

第 1、2 条决定谁在什么时候知道有事；第 3、4 条保证 bot 开口时没有落后于对话；第 5 条保证一件事只有一个人做。

## 规则

### 投递记录：谁收到

- **顶层消息**：每个成员 bot 和你各一条，发送者自己也有一条（不算未读）。
- **静音**：从静音开始的那条起，静音的 bot 收不到普通的顶层消息的记录，@everyone 也一样；只有换 leader 的通知例外，静音也收到，因为它改变了每个成员的规则。@ 它的消息、指派给它的任务回执照样有记录。线程不受静音影响。
- **线程里的消息**：线程的关注者，加上这次发送牵涉到的人：发送者、顶层消息的作者（他没有取消关注时）、被 @ 的成员。线程里的 @everyone 把每个成员都算进来，并让他们关注这个线程。取消了关注的人没有记录，除非这条 @ 了他；这一 @ 会让他重新关注，提示里会告诉他。
- **回复**：消息可以回复某一条（`reply_to`），被回复的 bot 收到的提示里标着「回复了你」。回复不能穿透静音。
- **有 leader 的群**（团队的 session 都是这种，见后面的[团队](#团队)）：
  - **成员收到什么**：只收找它的消息。一种是派给它的活：来自你、leader，或者你和 leader 引起的系统消息（`fromLead`），并且 @ 它、回复它、是指派给它的任务回执，或者 @everyone。另一种是别的成员问它事情：另一个成员发的、@ 它或回复它的消息。别的顶层消息不写它的记录，和静音一样，所以也不挡它发言；它关注的线程照样写记录，但不进待读、不叫醒它。成员的 @everyone、成员引起的系统消息（比如它给别人建任务的回执）都到不了别的成员：活只由 leader 派。成员发了 @everyone，`group_send` 的结果在「Undelivered mentions」里说明它只到了 leader。
  - **leader 收到什么**：你的消息和系统消息照群的唤醒方式收。成员发的、或者成员引起的消息，只有找 leader 的（@ 它、回复它、@everyone）才叫醒它，别的只写记录、不进待读。所以成员之间在线程里的问答、成员的进度都不叫醒 leader（leader 的模型通常最贵），它读那件活的线程时能看到。成员汇报时要 @ leader。
  - **一件活**：你或 leader 发的、@ 某个成员的顶层消息，是派给这个成员的一件活，它的线程是这件活的上下文。成员一次只做一件，每件新活换一个新座位（`pieceFor`）。别的成员在自己那件活的线程里问它事情，不算它的活：它在当前座位里回答，不换座位，座位记的活（`seat_task`）也不变。
  - **认领和任务**：成员只能认领派给自己的活（指派给它的任务，或者你和 leader @ 它的消息），不能把任务指派给别的成员，也不能改任务状态（只有 leader 能改，成员调用 `group_task` update 会被拒绝）。
  - **leader 的 prompt**：多一段怎么计划、派活（每条顶层消息 @ 一个成员，带完整的说明）、检查结果，并列出每个成员的介绍和模型，不带子 agent 那一段，也不带认领和拆任务（它派活靠 @，核对后自己把任务标成 done）。还说明成员之间会直接问事情、不叫醒它、不转移活；可以在派活时让一个成员直接去问另一个。成员汇报后，leader 看它验证了什么、怎么验证的、哪些没验证，不重复成员已经做过的检查，自己判断要不要再验证：小的（一条命令、看一眼文件）自己做，大的（补测试、整体 review）派给成员，并说清已经验证过什么。你的请求全部做完后，leader 用 `reply_to` 回复你那条请求，写结果、验证过什么和怎么验证的、没验证或遗留的事，所以结论出现在你提问的地方，派活、汇报、返工这些过程留在各件活的线程里。
  - **成员的 prompt**：多一段只做派给它的事；做完先尽量自己验证（跑测试、试一下、再看一遍改动），再在这件活的线程里 @ leader 汇报一次就停，说清改了哪些文件、验证了什么、怎么验证的（命令和结果）、哪些没验证；不发确认和进度；卡住了问 leader；能开子 agent 时派给它的活自己做。需要别的成员角色上的东西（代码在哪、测试为什么失败）时，在自己那件活的线程里 @ 它问一个简短的问题，只问信息、不派活；被别的成员问到时，在那个线程里简短回答、@ 对方，然后回去做自己的活，回答要花真功夫就说出来，让 leader 决定。prompt 里列出别的成员和他们的角色。别的只留消息、写法、约束和权限几段，没有线程、任务、提醒、礼节这些用不到的规则。成员的工具也只列出它用得到的（`group_send`、`group_send_draft`、`group_read`、`group_claim`、`group_react`、`group_members` 和 `search_chats`，见下面「bot 的群聊工具」）。
  - **成员卡住**：一轮失败了（被限流、出错、停下），或者要为这件活开新座位却建不起来、不再自动重试，这件活的线程里记一条 @ leader 的系统消息（`seat.piece_failed`），叫醒 leader：这件活的消息要么座位已经收下、不会再提示，要么在等一个起不来的座位，而「X's turn failed」「X couldn't join」不进任何人的待读，没有这一条，成员不会回来接着做，leader 也不知道。leader 在线程里 @ 成员让它接着做（座位还在这件活上，续用同一个会话，出错后的等待照常）或再试一次启动，或者把这件活交给别人；只有你能处理的错误（没登录、余额、套餐……）或自动启动已经暂停时，这条消息让 leader 去告诉你。提醒以后线程里没人说话，同一个成员再卡住也不重复；leader 回应过以后再卡住，会再提醒，不受顶层「X's turn failed」十分钟只记一次的限制。
  - **换 leader**：发一条 @everyone 的系统消息（`group.leader`），静音的成员也收到，新 leader 的提示里标「you were @mentioned」，已经开着的座位靠它知道新规则，下次开会话时 prompt 也跟着变。leader 离开群，群就没有 leader 了。
- **成员的一件活（piece）**：`workOf` 定每条待读属于哪件活：线程里的消息属于那个线程；你或 leader 在顶层 @ 它的消息是一件新活，就是它自己的编号；别的（系统消息、@everyone、顶层的回复）不属于哪件活，跟着当前的活一起送。座位记着它的会话在做哪件活（`group_members.seat_task`）。叫醒时（`pieceFor`）：当前这件活有新消息就先送它，否则送最早的那件；属于别的活的待读先不提示，等这件做完再说。要送的活和会话正在做的不是同一件时：会话忙就等这一轮结束，空闲就把座位换新（归档旧聊天，开新会话，不带简报，看过的记录全部清掉）。所以新活从一个空的上下文开始；回到一件老活时，新座位没给它看过那个线程，被 @（或被回复）时线程上下文照常附上：顶层的派活消息、@ 之前最近的 6 条回复和那条 @。成员的叫醒里，这件活的消息直接给全文（最多 8 条，`[For you, in full (already read):]`），座位收下就算看过、从待读里取走，它不用再 `group_read`；不再附「没完成的任务」。成员在顶层不做发言前的检查：顶层收到的只有派给它的活，每件活由自己的提示送到。如果拿它们来拦，认领手上这件时，会把还在等的下一件当成看过，从待读里取走，那一件就再也不会送到。所以 leader 一次派给它两件活时，它认领第一件不会被拦，第二件留在待读里，等这一轮结束再送。它认领后的提示是：做完在线程里 @ leader 回答，状态由 leader 改。
- **@everyone**：顶层的 @everyone 投给每个没静音的成员，标出「for @everyone」。
- **系统消息**按种类处理，见下面的「任务和系统消息」。
- **自动关注**：在线程里发言的人、顶层消息的作者、在线程里被 @ 的人。你也算：你发过的顶层消息和你回复过的线程，有新回复时算你的未读。
- **取消关注**：bot 可以带一个理由取消关注，线程里会记一行「@Ada stopped following this thread: 理由」（不写投递记录）；之后这个线程的普通消息不再投给它，被 @ 或者它自己在线程里发言，会让它重新关注。`group_follow` 带 `list: true` 列出它关注的线程：哪个线程、顶层消息开头、什么时候开始关注、为什么。

### 未读

一条消息对一个接收者算未读，当且仅当：不是它自己发的；不是它自己引起的系统消息；不是不记录的那类系统消息。被 @ 的总算未读。

「有哪些未读」是：算未读的投递记录里，编号在这个会话的读位置之后的。`group_inbox` 列出这些，什么都不改：每个地方一行「open:」，写着几条未读、有几条 @ 它、最新一条是谁什么时候发的、还没进过提示的有几条，最后一行「Next:」给出读它的 `group_read` 调用；`mentions: true` 只列有 @ 它的地方。群列表的未读点、线程链接旁的点，也是用你的投递记录和读位置算的。

### 叫醒和提示

- **待读**：投递给 bot、它还没读走的消息。一条记录进不进待读：
  - Everyone 方式（默认）下，算它的未读就进。
  - 「只叫醒被找的人」（Only who it's for）方式下，只有找它的才进：@ 它、回复它、指派给它、@everyone，以及你发的、没找任何人的消息（没 @ 谁、不是 @everyone，也不是回复某个成员的消息）。你回复 Ada 的消息只是找 Ada，别的 bot 照样写投递记录，只是不进待读，也不叫醒。
- **提示**：不带内容。每个会话一行：几条新的、从第几条到第几条、最新一条是谁发的、为什么找它（被 @、被回复、交接、@everyone、派了任务、有任务），**最近有动静的会话在前**。
- **什么时候发**：空闲的 bot，马上开一轮。正在忙的，**等 3 秒**再插进当前这一轮，这 3 秒里进来的都合在这一条提示里（从第一条进来时算起，后来的不会把它往后推）；3 秒内这一轮先结束了，就马上开新的一轮，不再等。插不进去，15 秒后再试；空闲时插不进去（比如正在压缩上下文），这一轮结束后再发。限流和出错后的等待见下一节。
- **每条消息只进一次提示**：待读里有还没出现在提示里的，才发新提示。bot 推迟不读也不会被反复催。
- **被 @ 进线程时附上线程上下文**：座位建起以来，这个线程还从没给它看到过时，提示里直接附上顶层消息、@ 之前最近的 6 条回复和那条 @。模型收到之后，线程的 boundary 记到附带的最后一条，顶层消息在顶层记为零散看过。是否附带按「给它看到过哪」（`group_seen.visible_boundary`）判断，这份记录压缩和座位换新都不清，所以已经被拉进过的线程不会再附一遍。

### 运行时出错：先等，同样的错三次就停

座位的一轮失败了，先读它的错误文字（`server/runtime-errors.ts`）：

- **哪一类**：限流（429、「rate limit」「too many requests」「model is at capacity」）、服务端出错（5xx）、连不上（ECONNRESET 之类）、流断了、超时、要重新登录、额度或余额用完、模型或套餐不对……
- **是不是终止性的**：用量上限、额度、模型找不到、流断了、要登录、余额、套餐。其中**要你处理的**（登录、余额、模型不支持、套餐不含这个模型、输入太大而运行时不是 Claude）既不等，也不算进同样的错三次，运行时马上停下（见下面）。
- **指纹**：去掉密钥、邮箱、网址参数和用户目录，转小写，长串十六进制和数字都换成占位，空白合并，取 SHA-256 的前 16 位。同一种失败，请求 id、token 数、时间不同，指纹也一样。

**等一会儿再说**（10 秒起，最多 5 分钟）：限流、服务端出错、连不上、流断了，以及时间能解决的终止性失败（用量上限、模型找不到），之后不叫醒它：第一次等 10 秒，连着再失败就翻倍，最多 5 分钟，每次加上 0 到 10% 的随机量。这期间进来的消息照样进它的待读，不发提示；@ 它的，@ 的去向里先算丢了（限流算 quota，别的算运行时拒收）。等完了看一次待读：有还没进过提示的，一条提示说全部；全都提示过了就不发。超时和没分出类的错误不等。一轮正常结束就清掉等待。

**同样的错三次就停**：要你处理的错误以外，每次失败按指纹计数，指纹变了从 1 重新算，一轮正常结束或你 @ 它才清零。第 3 次时它的运行时停下，群里记一行「X stopped after 3 repeated runtime errors with the same fingerprint (…). Last error: … Restart after the runtime/tooling issue is fixed: @mention X to restart it, or its next message starts it again.」。停下不清计数：重新开始后同样的错再来一次，就第 4 次停下。

**要你处理的错误也停下**：没登录、套餐不含这个模型、余额用完、模型不支持、输入太大时，运行时马上停下。群里记一行「X's turn failed: …」，和别的失败一样，同样的错 10 分钟内只记一次。

**停下之后，下一次叫醒重新开始**：停下的 bot 的待读照样攒着，不发提示，@ 它的算运行时拒收；下一次叫醒让它重新开始，一条提示说全部。叫醒是：

- 一条进了它待读的群消息，**谁发的都算**：你的、别的 bot 的、任务的系统消息。
- 它的提醒响了。这次启动被断路器拒绝时，提醒的这次叫醒丢掉。

等待到期、它自己的一轮结束都不算叫醒。自动启动要先过两个断路器（`server/breakers.ts`）：

**终止性失败的断路器**：证据是同样的错三次的停下（种类 `fingerprint_fence`）和余额、模型不支持、输入太大的停下（`sticky_runtime_error`），各带错误文字的指纹；没登录和套餐的停下不是证据。中间没有一轮正常结束时，同一个指纹的第 2 次，或者任意的第 3 次，就断开：之后 1 小时的自动启动都拒绝，群里记一次「X: Automatic wake paused until <UTC 时间> after repeated runtime failures (<种类>). The next message, reminder or manual start after that retries; a manual start lifts it now. @mention X to start it now.」（每次暂停记一次）。1 小时后的第一次叫醒是唯一的一次试探，租期 30 分钟，这期间别的自动启动也拒绝。试探的一轮正常结束就合上，计数清零；试探又停下，就再断开，等 4 小时，再一次 24 小时，之后一直是 24 小时；租期到了还没有结果，也按下一步断开，从租期结束时算。没断开时，一轮正常结束也把计数清零。

**过早退出的断路器**：运行时启动后不到一分钟就退出，算一次过早退出；跑过一分钟的不算，计数清零。连着 3 次，群里记一行「X: Automatic wake paused after 3 early exits. @mention X to start it again.」，之后自动启动都拒绝，只有手动启动才行。只数没登录和套餐的停下；别的停下归上一个断路器管。

**你 @ 它就是手动启动**：停下、两个断路器、等待、同样的错的计数都清掉，建不起来的座位也从头试，一条提示说全部。只在等待中、没被停下也没暂停的 bot，@ 它不会提前叫醒，照样等完。

**座位建不起来**（1 秒起，最多 30 秒，5 次）：1 秒、2 秒、4 秒、8 秒后各再试一次；这期间进来的消息先攒着（@ 的去向里 in flight），下一次试时一起带上，再失败就算没在运行（not_launched）。第 5 次失败就不再自己试，群里记一行，要告诉它的留给下一次叫醒。下一次叫醒是一次自动启动：还建不起来，就暂停自动启动（种类 `spawn_error`，不算进上面的计数）：5 分钟，每失败一次翻倍，最多 6 小时，不限次数；群里记一行「X couldn't join: …」，后面接暂停的文字。暂停结束再加上这个座位固定的 0 到 60 秒，不等新消息就自己再试一次（只在暂停全是建不起来引起、又有被拒或没送到的叫醒时）。建起来就清零。失败的原因要你处理（比如没登录），第一次就停下，记「… Fix that, then @mention X to try again.」，自动启动都拒绝，只有你 @ 它才再试。只在第一次和停下时记，中间几次不记。

这些状态都只在内存里，pocket-bots 重启就从头算，代价是：重启后，暂停中的 bot 会被重启补课叫醒一次。待读在 SQLite 里，所以不会漏掉消息。成员离开群、群被删时一起清掉。

### 运行时的看护：排队启动、启动超时、看不到的轮次、卡住的运行、压缩一直失败

这些都在 ChatService 里（`server/supervision.ts` 是常数和启动队列），所以不只管座位，bot 的每个聊天都一样。

**排队启动**（同时 6 个，间隔 0.5 秒）：整个 pocket-bots 进程只有一个启动队列，所有群和聊天都排在里面。一个聊天要开运行时（新会话、续接，或者空闲关掉以后再来一条消息），先排队：同时最多 **6 个**在启动，每个比上一个晚至少半秒开始（同一个聊天紧接着又启动一次不用等）。占着的位子在会话打开、第一条输入写进去以后让出，不等运行时回话。一个群最多 6 个 bot，一条 @everyone 正好让每个成员都启动。

**排队时来的消息一起带上**：启动还在排队或正在打开会话时，发给这个聊天的消息不另起一轮，先攒着，和第一条合成一条输入（中间空一行），用第一条的 id；每一条都在运行时收下那条输入时算收下（`input.accepted` 对每个 id 都发一次），发的人都拿到同一轮。第一条已经写进去以后来的，照常插进这一轮。

**启动超时**（2 分钟）：从拿到位子开始算，2 分钟内运行时要报来第一个事件，否则这次启动失败，不让聊天一直「启动中」（比如 CLI 卡在登录提示上）。算数的事件是运行时自己的：pocket-bots 自己记的「这一轮开始了」、会话 id、你发的那条消息本身都不算，运行时在排队时就当作收下的（Grok）的「收下」也不算；一轮结束算（失败的也算，那是运行时的错，照上面的规则处理）。失败分三种：会话没打开（2 分钟到了还没打开，之后打开了就马上关掉）、第一条输入没写进去、写进去了但运行时什么都没报。第三种结束运行时（SIGTERM），这一轮在聊天里记成失败，文字是「X did not finish starting on this machine. Check that X is installed, logged in, and can run non-interactively, then retry starting this agent.」。ChatService 发 `start.failed`；座位的这种失败**按座位建不起来处理**（见上面），群里记「X couldn't start: …」；告诉它而运行时没收下的消息再说一次，@ 的去向里先算没在运行（not_launched）。运行时报来第一个事件就发 `start.ready`，座位的建不起来的计数清零。这样一个一直卡在登录上的座位试 5 次就停，不会每条消息都卡 2 分钟。

**看不到的轮次**（30 秒）：写进去不等于跑起来了。会话空闲时写进去一条、开始一轮，如果运行时自己会报这一轮（`session.liveTurn`），30 秒内既没报这一轮、也没报任何事件，聊天就回到空闲：这一轮记成取消，聊天里记一行「X didn't show this turn within 30 seconds, so the chat is idle again.」，还在等运行时回话的发送也返回失败，不再干等一个永远不来的结束。适用的运行时：Codex（`turn/start` 回话或 `turn/started`）和 Pi（RPC 的 `prompt` 回话或 `agent_start`）。不适用的：Claude（Agent SDK 自己排队，没有「收下了还没开始」这一步）、OpenCode（命令和 `/compact` 做完才回话，长的压缩会被当成没开始）、Grok 和 DeepSeek Harness（ACP 的 `session/prompt` 一轮结束才回话）。启动的第一条输入不归它管，归上面的启动超时。

**卡住的运行**（15 分钟，SIGTERM 后 10 秒）：每分钟看一遍正在跑的轮次。从最后一个运行时事件（或这一轮开始）起 15 分钟什么都没有（在等你审批的不算）：

- **进程没了**：这一轮卡住了：SIGTERM，10 秒后进程还在就 SIGKILL；这一轮记成失败，文字是「Runtime stalled: no runtime events for 15m (queued=N)」；运行时还没收下的输入（插话、排着的消息，N 条）在一次新的启动里再发一次，续接同一个会话，用原来的 id，所以座位的提示收下时照常算收下。群里记一行「X's run stalled (…) and its process was gone, so pocket-bots restarted it.」。这不算运行时出错：不等、不算进同样的错三次。
- **进程还在**（或者适配器说不清，比如 Claude 的进程在 Agent SDK 手里）：只记一次日志，不动它，安静不等于卡住。只有运行时自己说没有轮次在跑（`liveTurn` 是 false）时，聊天回到空闲，记一行说明（忙了 10 分钟以上又没有进展，是漏了这一轮的结束）。

**压缩一直不结束**（5 分钟）：运行时报了压缩开始（Pi、OpenCode、Codex 会报），5 分钟还没报结束，聊天里记一行「Context compaction is still running; no finish was seen.」，只是说明，不做别的。

**压缩一直失败的会话不再续接**（3 次）：Pi 用一次请求总结整个会话，会话大到这次请求放不进模型以后，每次续接都会再压缩失败。Pi 报来的压缩结束没有结果、也不是被打断，就是失败（压缩条目记成 failed，这一轮也算失败）。每个聊天记下这个会话、这个模型连着失败几次（`chats.compaction_failures`，存在 SQLite 里，重启不清；只有 id、模型名和次数）。压缩成功就清零；换了会话或模型也从头算。只对 Pi 计数。连着 3 次以后，这个会话不再续接：

- **座位**：下次叫醒时照座位换新处理，归档旧座位，开一个新座位，从简报开始（简报开头说明是因为压缩不下去才换新），群里记一行「X's session failed context compaction too many times in a row to be resumed, so X starts over in a new session with a briefing of the group.」。
- **别的聊天**（以及没经过叫醒就打开的座位）：下次启动开一个新会话，聊天里记一行说明，ChatService 发 `session.reset`；是座位的话群里也记一行。
- Pi 的新会话 id 每次都带一段随机后缀，因为 Pi 的 `--session-id` 遇到已有的会话 id 会打开它。

### 读和搜索

| `group_read` 的参数 | 读什么 | 怎么记 |
|---|---|---|
| `unread: true`，不指定地方 | 待读里的全部，旧的在前，一次最多 40 条 | 每条记为零散看过，从待读取走 |
| `unread: true`，加 `thread` 或 `top_level: true` | 这个会话读位置之后的消息 | 一定接得上，boundary 前进到最后一条 |
| `thread`，或者什么都不带，或者 `before` | 一个会话最新的几条，或某条之前的 | 接得上就推进 boundary，接不上就逐条记零散看过 |
| `around: N` | 第 N 条所在会话里，它前后的几条 | 定位读：只逐条记零散看过 |

「接得上」：读到的这一页从会话开头开始，或者这一页最早的一条不晚于读位置；从读位置往后读的，总是接得上。其他规则：

- 读到空的，不记看过。
- 只有接得上的读和读到空的，才算「最近一次读了这个会话」（发顶层前的确认看的就是这个）；逐条记的读、定位读、读待读都不算。
- boundary 只往前走，往回翻不会把它拉低。
- 一个会话的读只记这个会话：读线程不推进顶层；读线程时顺带显示的顶层消息，在顶层记为零散看过。
- 读位置跟着「看过」走：从读位置往后，一条条消息只要模型都看过，读位置就往前推；碰到第一条没看过、又算它未读的就停。bot 自己发的消息、它没收到的消息（静音时的普通顶层消息，有 leader 时不是派给它的）不算断点。
- 读一个会话的未读时，模型已经看过的（比如搁置时给它看过的）不再重复，只用一行说明有几条、怎么再看；最后说明读位置从哪条移到了哪条。

`group_search` 对每条命中只给出处、发送者、时间和匹配处前后的一段（前 80 字、后 120 字，匹配的部分用 `<match>` 标出），**不算看过**。预览不够时，用 `group_read` 带 `around` 读它前后的消息。

### 看过的记录

每个 bot、每个会话记两样：**boundary**（到这一条为止都看过）和 boundary 之后**零散看过**的编号（最多 2,500 个，保留最新的）。一条消息算看过，当且仅当它不晚于 boundary，或者在零散看过的里面。

| 怎么看到的 | boundary | 零散看过 |
|---|---|---|
| 一次接得上的读 | 前进到读到的最后一条 | |
| 一次接不上的读、定位读、读待读 | | 读到的每一条 |
| 被 @ 进线程时附带的上下文 | 线程的 boundary 前进到附带的最后一条 | 顶层消息那一条 |
| 被搁置时给它看的 | | 给它看的那几条 |
| 自己发的消息 | | 这一条 |
| 不带内容的提示、搜索的预览 | | |

只收到提示、还没读的，不算看过。

**只在看到它的那个模型上下文里算数**：

| 什么时候 | 看过的记录 |
|---|---|
| 新座位 | 全部清掉，包括「给它看到过哪」 |
| 座位换新 | 作废，「给它看到过哪」留着 |
| 压缩上下文（运行时报来 `compaction` 条目：Claude、Codex、Pi、OpenCode） | 作废，「给它看到过哪」留着 |
| 座位关掉后续接同一个会话（空闲 15 分钟关掉，或 pocket-bots 重启） | 保留 |
| 续接，但运行时从不报告压缩（Grok、DeepSeek Harness） | 作废：不报告压缩的运行时，续接证明不了上下文还是原来的 |

作废就是 boundary、零散看过的和「最近一次读」都清掉，读位置和待读不动。之后它发言，检查找不到证据，就像第一次碰这个会话一样先搁置一次，等它再读。「给它看到过哪」只用来决定附不附线程上下文（见上面「叫醒和提示」）。bot 读到的消息每条都写全发送者的名字，压缩后没有别的要补。

### 发言前的检查

发言（`group_send`、`group_send_draft`）、认领（`group_claim`）、改任务状态（`group_task` update）之前，对要发往的会话依次检查（有 leader 的群里，被带的成员在顶层不检查，原因见上面「成员的一件活」）：

1. **待读**：这个会话里投递给它、还没读走的消息。
   - 有它没看过的：**搁置**，给它看其中最新的 3 条。
   - 都看过了：继续。
2. **第一次碰这个会话**（没有待读，也没有 boundary）：拿出会话最近的 3 条。
   - 有没看过的：**搁置**，给它看这几条。
   - 都看过了：以最新那条为界，继续。
   - 会话是空的：继续。
3. **只对发言**：从 boundary（第 2 步得出的界，或者它的 boundary）往后数，除掉零散看过的、它自己发的、它自己引起的豁免类系统消息：
   - 顶层数**它的投递记录**，所以静音期间它没收到的消息不算；
   - 线程数**线程里的全部消息**，因为线程不受静音影响；它从没读过的线程，从顶层消息往后数。
   - 有就**搁置**，给它看最新的 3 条，并告诉它一共几条、还有几条没给它看、怎么用 `group_read` 读。如果这几条就是全部，它的读位置前进到最后一条。

豁免类系统消息是那些内容全在它自己的请求或回执里的：成员变化、建任务、指派回执、把消息变成任务。任务状态变化的消息不豁免：它带着任务标题，改状态的回执里没有。

被搁置时给它看的都记为看过，所以它再发一次，就会轮到更早的、还没给它看的那些。实际上它通常被搁置一次之后，就按提示用 `group_read` 读完再发。

### 草稿

- 被搁置的发言存成这个会话的草稿：内容、回复对象、一个固定的发送 key（同一份草稿发两次只会发出一条）、被搁置的次数。每个 bot 每个会话一份，10 分钟过期。
- 同样的内容再被搁置，次数加一；发了新的内容，就换成新草稿，次数从 1 开始。
- `group_send_draft` 原样发（会再检查一次）；带 `thread` 选哪个会话的草稿，不带就是最近的那份；`discard: true` 丢掉；`anyway: true` 跳过检查。被搁置 3 次以后，提示才告诉它可以用 `anyway`。

### 发顶层前确认一次

bot 最近一次读的是某个线程（比它最近一次读顶层更晚），却往顶层发：不发，把话存成顶层草稿，提示它「你最近读的是线程 #N」。属于线程就发到线程；确实要发顶层，用 `group_send_draft` 发出草稿。回复一条顶层消息（`reply_to` 指向它）不用确认：回复本身就说明了要发在顶层，比如 leader 读完成员的汇报，回复你的请求告诉你结果。

### 任务和系统消息

任务就是一条被标成任务的**顶层消息**，状态 `todo → in_progress → done`，`closed` 表示不做了，最多一个负责人。bot 按允许的转换改状态；你是群主，可以设成任何状态。认领时先认领的生效；认领失败是一把锁。

每个任务有一个版本号，认领、放下、改状态、指派、改卡片都让它加一，`group_task list` 里显示为 `rev=N`。指派时带上读到的版本号（`expected_revision`），任务在这之后变过就拒绝，告诉它现在是什么样，而不是覆盖别人的改动。已经 done 的任务不能再指派；指派给现在的负责人什么都不变；指派不会开工，被指派的人认领了才是 in_progress。

**放下**只去掉负责人，**状态不变**：负责人和状态是两回事，in_progress 的任务放下以后还是 in_progress，等别人认领接着做。done 的任务不能放下，没人负责的也不能（「task is not assigned」）；任何成员都能放下，历史里记着是谁把任务从谁手里拿下来的。

你在输入框里打开 **As task** 再发，这条消息直接就是一个任务（todo、没人负责），不记系统消息；只能用在顶层。

每种系统消息都声明了分类：「起因者不算未读」的，或者「不写投递记录」的。

| 什么时候 | 发在哪 | 分类 |
|---|---|---|
| 成员加入、离开 | 顶层 | 起因者（你）不算未读，bot 照常收到 |
| bot 建任务，没有负责人：「📋 2 new tasks created: …」 | 顶层 | 起因者不算未读 |
| bot 建任务，指定了负责人：「📌 Assigned @Rex to task #9 …」，指定自己则是「📌 @Ada started …」 | 顶层，@ 负责人，静音也收到 | 起因者不算未读；但「被 @ 的总算未读」优先，所以指定自己时，这条回执也会叫醒它自己 |
| 把消息变成任务（你或 bot）：「📋 Ada converted a message to task #3 …」 | 顶层 | 起因者不算未读 |
| 改状态（你或 bot）：「✅ Cody moved #3 "…" to Done」 | 任务自己的线程 | 起因者不算未读，线程的关注者收到 |
| 你认领、放下、指派：「📌 the user claimed #3 …」「🔓 the user released …」「📌 the user assigned #3 … to Cody」 | 任务自己的线程 | 同上 |
| 删除任务（你，或建任务的 bot）：「🗑 the user deleted #3 …」「🗑 Cody deleted #3 …」 | 顶层 | 不写投递记录 |
| 某个 bot 这一轮失败了 | 顶层 | 不写投递记录 |
| 有 leader 的群里，成员在一件活上卡住了：「⚠️ @Lead: Cody's turn on this piece failed: …」或「⚠️ @Lead: Cody couldn't start on this piece after 5 tries: …」 | 这件活的线程，@ leader | 起因者不算未读；leader 被叫醒；提醒以后线程里没人说话就不重复 |
| bot 不再关注某个线程 | 那个线程 | 不写投递记录 |
| bot 向你提问 | 顶层，作为这个 bot 的消息 | 不写投递记录 |

几点要注意：

- bot 认领、放下、给已有的任务指派负责人，**不发系统消息**，任务标签会变。
- 给已有的任务指派负责人，**不会通知**被指派的 bot。要它开工，得 @ 它。只有建任务时带上负责人，才会发一条 @ 它的回执。
- 建任务时，每个标题先作为建任务那个 bot 自己的消息发出去（大家照常收到），再变成任务。带负责人时任务一次建好：给别人的是 todo、留给那个人，给自己的直接 in_progress；版本号从 0 开始。
- 系统消息里任务的标题用卡片当前的标题。

任务号就是它那条消息的编号：task #12 就是消息 #12，它的线程是线程 #12。消息号和任务号如果是两套小整数，bot 很容易搞混、把帖子发错线程，所以合成一个。

### 任务卡片

任务除了挂在哪条消息上，还有自己的一张**卡片**：

- **标题**：变成任务时抄那条消息的文字（bot 建任务时就是它给的标题）；**描述**：细节或验收标准，一开始没有。
- 谁建的（变成任务的人、认领时顺带变成任务的认领者、建任务的 bot）、完成时间（变成 done 时记下，离开 done 时清掉）、关闭时间和关闭的人（变成 closed 时记下，重开时清掉）、开始时间（todo 或 closed 变成 in_progress 时记下，in_progress 退回 todo 时清掉）。
- **历史**，只追加：建任务（`created`，变成任务的带 `convertedFromMessage`）、负责人变化（`assignee_changed`，认领、指派、放下都记，带原来的负责人）、状态变化（`status_changed`，带 from、to，你改的带 `forced`）、关闭（`closed`）、重开（`reopened`）、改卡片（`amended`，带新的版本号和每个字段改之前、改之后的内容）。每条有一个全局的序号，所有任务的历史排在一个顺序里。

`group_task` 对卡片的操作：

| 操作 | 说明 |
|---|---|
| `amend` | 改标题（1 到 10,000 字）、改描述（最多 50,000 字）或 `clear_description` 清掉描述，至少改一样；什么都没变就拒绝（「task amendment makes no changes」）。**任何成员都能改**，卡片上写了谁的名字不代表什么。卡片和历史在同一个事务里写。不发系统消息，也不过发言前的检查。返回新的版本号和这次改动在历史里的序号 |
| `show` | 一个任务现在的卡片：状态、负责人、版本号、谁建的、`Current title:`、`Current description:` |
| `history` | 卡片现在的样子，然后按顺序列出每一次变化：序号、时间、谁、什么事、内容（JSON） |
| `delete` | 只有建任务的 bot 能删（你也能删）。删掉任务和它的历史，消息留着；之后再把这条消息变成任务，是一个新任务、新的历史。别人删会被拒绝，并建议把任务关掉 |

**改过的卡片**：消息本身永远不改。bot 读到一条改过卡片的任务消息时，下面附上当前的卡片：

```
#3 · the user · 2026-10-16 10:02Z · [task #3 · done · Cody]
修一下登录页
[task #3 amended: the card supersedes this message's text (rev=3, by Rex, 2026-10-16 11:00Z)]
Current title: 修一下登录页
Current description: Safari 和 Chrome 都要能登录；不加新依赖
```

只有改过卡片才附（看的是历史里有没有 `amended`，不是版本号，认领、改状态也会让版本号变）。`group_task list` 显示卡片的标题，有描述的另起一行；任务看板显示卡片的标题。你在界面里还不能改卡片（接口已经有了）。

### @ 的去向

每条你或 bot 发的消息，记下它 @ 的每个成员和 @ 原文怎么写的（之后 bot 改名也按原文显示）。系统消息里 @ 负责人不算。在线程里 @ 一个成员，本来就会投给他、让他重新关注，不需要别的补救。

**发出时**：@ 了群外的 bot（你的 bot，但不在这个群里），或者谁都不是的名字，`group_send` 的结果在「Sent as #N.」后面列出「Undelivered mentions — partial result」：消息已经发出去了，不要再发；每个没送到的 @ 一行，原因（不在群里 / 没有这个名字）、后果（这一下没通知任何人）、怎么办（群外的：只有你能把它加进群，要马上找它就用 `ask_bot`；名字不对的：是字面上的名字就放进 `code`，否则只发一条改正后的 @）。反引号里的 `@名字`（行内代码或代码块）是字面的：不通知谁，也不算没有这个名字；界面上也不高亮。

**`group_mention_delivery`**：给自己发的一条消息的编号，每个被 @ 的成员一行：

| 结果 | 什么时候 |
|---|---|
| **delivered** | 它的模型读到了：从待读里读走了，或者读位置、看过的记录已经过了这条 |
| **still in flight**，不要下结论 | 还在它的待读里。括号里说到了哪一步：还没提示（座位正忙或正在建）、提示发了座位还没收下、座位收下了还没读 |
| **LOST**，限流（quota） | 告诉它的那一轮因为限流、额度失败了（Grok 免费额度被限流就是这种）；建议换人或晚点再试 |
| **LOST**，运行时拒收（runtime_error） | 告诉它的那一轮因为别的错误失败了；建议换人 |
| **LOST**，没在运行（not_launched） | 它的座位建不起来（群里记一行「X couldn't join」），或者这个 bot 被归档了；建议换人或者让它跑起来 |
| **LOST**，其他（unclassified） | 读之前离开了群 |
| **UNKNOWN** | 没有投递记录 |

这些都从已有的记录推出来：每条投递记录记着最近一次告诉它的提示（提示发出前就记上）、座位收下了没有（运行时接受了这条输入）、为什么没送到（座位建不起来；或者它被告知、还没读的时候，这一轮失败了，按错误文字分成限流和其他）。之后再有提示告诉它，失败就清掉，回到 in flight：待读记录不会丢，这条消息还在它的待读里，下一次给它的提示会再告诉它。只给类别，不给错误原文：那是对方的事，发送者只需要决定是等还是换人。

然后列出这条消息还送到了谁、读了没有，以及当时在群里却没收到的（静音、或者不在那个线程里）。别人的消息查不了，和不存在的消息一样回答。

### 座位、换新和重启

- 每个成员 bot 在每个群里有一个座位，是这个 bot 自己的一个普通会话，用它自己的模型、审批模式、技能和 MCP。群第一次叫醒它时才建。座位的 system prompt 里多一段讲怎么在群里协作。bot 之间私下说话用 `ask_bot`，不在群里开私聊。
- **座位在哪个目录**：群设了工作目录（`groups.cwd`）就在那里，没设就在 bot 自己的工作目录。会话开始以后不能换目录，所以座位要去的目录（群的，或 bot 的）和它现在的不一样时（你改了群的目录，或改了 bot 的），它下次被叫醒、空闲时换新座位，和下面的换新一样带一份简报，开头说明目录从哪换到了哪（简报里操作的相对路径还是旧目录的）；忙着的座位先跑完这一轮。改群的目录时群里记一条 `group.folder` 系统消息，只留作记录，不进谁的待读、不叫醒谁（`skip`），所以不会为了换目录让每个 bot 白跑一轮。目录必须是本机上存在的文件夹，`~/` 会展开；不存在就拒绝，什么都不改。
  **额外文件夹不算换目录**：群还有一列额外文件夹（`groups.extra_folders`，上限 20，校验同上），每个座位的聊天上有一份副本。它变了，座位不换新、不带简报（不走上面那条路径，主目录变了才走）；每个座位的聊天拿到新列表，空闲的会话关掉、下一次输入时续接并带上新的目录，忙着的跑完这一轮再生效（Codex 的会话不关，就地换，下一轮生效），新座位建好后再对一次。群的工作目录换成其中一个额外文件夹时，它从列表里去掉（座位反正要换新，不另记消息）。群里记一条 `group.folder` 系统消息，同样只留作记录，不叫醒谁。agent 靠 system prompt 的「Extra folders」段，或续接时放在下一条输入前面的说明知道最新的列表（Claude、Codex 原生支持，其他 CLI 靠路径访问，见 design.md §5.1）。群的窗口里直接加减，座位自己的聊天里只读。
- **子 agent**：运行时能开子 agent 的座位，没有 leader 的群里 prompt 在「提醒和 @」和「写法」两段之间多一段「Sub-agents」：每个子 agent 都是从零开始的新会话，要把需要的东西重读一遍，所以小活和中等的活自己做；只有大的、能拆成几块并行的活，或者会让它长时间顾不上群的活，才交给子 agent；先回话再分派；子 agent 什么都看不到，要交代完整；**只有你在群里说话**，告诉每个子 agent 不要用群聊工具（`group_send`、`group_send_draft`、`group_claim`、`group_task`、`group_react`、`group_reminder`），这一条要紧，因为 Claude 的子 agent 默认继承 MCP 工具；结果自己核对后再报；子 agent 都做完、结果都报了才停。有 leader 的群里，leader 没有这一段（动手的活派给成员）；成员的规则里换成一句：派给你的活自己做，leader 已经拆过了，只有能拆成几块大的、值得并行的才开子 agent，并且不让它用群聊工具。以前这一段让每个座位把超过几次工具调用的活都交给子 agent：基准测试里 Haiku 成员把整件探索交给一个 Explore 子 agent，多出一个带着约 22K token 首个请求的新会话，占了整个群 37% 的 token。能开子 agent 的运行时：Claude（`Agent`）、Codex（`spawn_agent`）、OpenCode（`task`）、Grok Build（`task`）；Pi 自己没有，不加这一段。由运行时接口的 `capabilities.subAgents` 决定。
- **座位换新**：座位空闲超过 1 小时、上下文超过 128k token 时，下次被叫醒就换一个新座位，从一份约 8k token 以内的简报开始：
  - 它看过的最近 25 条消息（每条约 2k、整段约 4k token 上限）；
  - 正在用的文件，重新读出当前内容（最多 14 个，2 小时内碰过的现在重读，每个约 700 token；名字像密钥的只列路径）；
  - 最近 12 次操作（失败的标 `!failed`）；
  - 分给它、还没完成的任务。
- **重启后补课**：见例子的第 9 步。有 leader 的群里，成员不补课：只把派给它、它的座位还没收下的消息重新告诉它，还是一次一件活。
- **prompt 改了，续接的会话也要知道**：Claude Code 和 Codex 续接一个会话时，忽略新传的 system prompt，还用这个会话开始时的（`packages/runtime/test/live-prompt-resume.ts` 在真 CLI 上验证：续接时新 prompt 里加的一句，模型不知道）。所以每个座位记下它的会话按哪个 prompt 跑（prompt 的哈希，`chats.standing_prompt`）；续接时哈希变了，这次续接后的第一条输入前面先放上完整的新 prompt，标明它取代原来的（`<pocket-bots-standing-prompt-update>`）。之前的对话一点不动，prompt 缓存还有效。哈希里不算每天会变的部分（记忆的当前内容、最近的工作），不然每天都要重发。续接一个还没有记录的会话，只记下、不发，所以第一次上线不会给每个座位都发一遍。Grok、OpenCode、Pi 每次开会话都重新带上 prompt，不用这样做。只用于座位，bot 自己的会话不发。
- 审批、密钥、登录和需要你私下处理的事不出现在群里，都在 bot 的座位里；群里显示「X needs your approval」，点一下进去处理。bot 问你的问题例外：作为它的消息出现在群里，答案回到它的座位（见下面「bot 的附件和提问」）。

### 提醒

提醒是 bot **给自己**定的：以后某个时候叫醒它，处理一件现在还没法处理的事（等构建跑完、明早看一下结果）。`group_reminder`：

- **定**（schedule）：标题（最多 500 字）、挂在哪条消息上（必须给），以及 `delay_seconds`（相对时间，优先用）或 `fire_at`（UTC 的绝对时间，一年以内；超过 24 小时会提醒它是不是想写相对时间）。`repeat` 让它重复：`every:15m` / `every:2h` / `every:1d`（至少 30 秒，最多一年）、`daily@09:00`、`weekly:mon,fri@09:00`。每天、每周的按定的时候的时区算（这台电脑的，或者 `tz` 指定的），之后电脑换时区也不变；夏令时切换时 09:00 还是当地的 09:00。只给 `repeat` 时，第一次在下一个符合规则的时间响。
- **列出**（list）：自己的、还在等和已经响过的，最早的在前；过了时间还没响的标 OVERDUE；`all: true` 连取消的一起。id 用 # 后面的 8 位，也可以更短，只要不重。
- **推迟**（snooze）：`by`（30m、2h、1d）之后再响；响过的也能推迟，回到等待。
- **改**（update）：标题、`fire_at`、`in`（从现在起多久）、`repeat` 四样里改一样；只有还在等的能改，响过的要先推迟回来。
- **取消**（cancel）、**看记录**（log）：每次定、响、推迟、改、取消都记一行，最新的在前。

只能看和改自己的提醒。每次改动都让版本号加一，响的时候按读到的版本号改状态，所以一个提醒只会响一次，和改动同时发生也不会重复。

**响的时候**：一次性的变成 fired；重复的继续等下一次，下一次从「这次该响的时间」和「现在」里较晚的那个往后算，所以停机错过的几次不会一次次补，只补响一次。**只叫醒它自己**：它的座位收到一段

```
🔔 Reminder #0a1b2c3d (one-time) — #12 — "check the build"
(to snooze/cancel: group_reminder)
```

重复的还有「Next iteration: 下次的时间」，停机期间错过的标「catchup ·」。这段和待读提示一起发；座位这时收不了（比如正在压缩上下文），这一轮结束后再发；它没有座位时，会为它开一个。群里不发任何消息：要告诉别人，它在响的时候自己 @ 对方。

pocket-bots 只用一个计时器，盯所有群里最早的那个提醒，提醒有改动就重新设；启动时，过了时间的提醒补响。界面上，提醒只读地列在任务看板下面。

### bot 的附件和提问

bot 在群里的回复可以带文件和问题，和一对一聊天一样，你对问题的回答回到问的那个 bot；审批、密钥和登录不出现在群里；bot 之间的交接以文字为主。这两样不改变上面的投递机制。

**附件**（例子的第 15 步）：

- `group_send` 的 `files`：本机的文件路径，最多 6 个；相对路径从座位的工作目录算，`~/` 是家目录。每个都要在、是文件，大小照你的附件的限制（图片 10 MB，文本超过 1 MB 按其他文件算，其他文件 25 MB）；不行就拒绝这次发送，告诉 bot 哪个文件有什么问题。
- **以文字为主**：bot 的消息必须有文字；只带文件、没有文字会被拒绝（「Write the message too」）。座位的 prompt 写着：文字自己就要把事说清楚，读的人需要文件本身时才附上，并说明每个是什么。bot 都在这台电脑上，所以文件能随消息一起给。
- 发出时复制到群的文件夹（`groups/<群>/files/`），和你的附件一样存成 `GroupAttachment`，之后原文件改了、删了，群里的不变。同一个 idempotency key 重发，复制的文件删掉，只回「Already sent」。
- 被搁置的发言，文件路径跟草稿存在一起（`group_drafts.files`）；同样的文字带了别的文件，算新草稿。
- 给别的 bot：读群消息时每条消息下面列出附件的名字、类型和路径；提示里附带消息的时候（被 @ 进线程的线程上下文、重启补课的批次），你和**别的 bot** 的文件一起给它，最新的 8 个，不给它自己的。
- 界面上 bot 消息的附件和你的显示方式一样：群文件夹里的图片显示缩略图，点开看大图；其他文件显示文件名。

**提问**：

- 运行时这边，每个 CLI 自己的提问工具都变成一个种类为 question 的审批（`packages/runtime/src/questions.ts`），回答也按各自的格式送回：

  | 运行时 | 工具 | 怎么到 pocket-bots | 回答怎么送回 |
  |---|---|---|---|
  | Claude Code | `AskUserQuestion` | `canUseTool` | `updatedInput.answers`，按问题原文作键（Claude Code 要这样；界面的表单按 header 作键，这里换过来） |
  | Codex | `request_user_input` | app-server 的 `item/tool/requestUserInput` | 每个问题的 id 对应 `{ answers: [...] }`；Dismiss 是空的 answers。只在 plan 模式下有这个工具，pocket-bots 不用 plan 模式，所以一般不会出现；问题标着 `isSecret` 的，整个审批标成 secret |
  | OpenCode | `question` | 先过一次 `question` 权限（座位规则里放行，旧会话自动放行），再来一个 `form.created`（`metadata.kind` 是 question） | `session.form.reply`，字段 `q0`、`q1`… 对应选项的值（多选是列表）；Dismiss 是 `session.form.cancel`。别的种类的表单直接取消（pocket-bots 不显示） |
  | Grok Build | `ask_user_question` | ACP 扩展请求 `_x.ai/ask_user_question` | `{ outcome: "accepted", answers: { 问题原文: 回答 } }`；Dismiss 是 `{ outcome: "cancelled" }`，Grok 会告诉模型没有用户回答，bot 照样知道你没答 |
  | Pi | 没有 | | |

  能问的运行时，座位的 prompt 里多一句：只有你能定的事用这个工具问，问题会作为它的消息出现在群里，答案回到它这里，不会叫醒别的 bot（`capabilities.questionTool`）。
- ChatService 发 `permission.requested`，审批不再等了发 `permission.resolved`（你回答了，不管在群里还是座位里，`answered`；这一轮结束了，`ended`；聊天关了，`closed`），按聊天依次发。
- 群这边（`GroupChats.onPermission`）：座位的审批是问题、又不是 secret 的，作为这个 bot 的一条顶层消息放进群里，文字是问题本身（「哪天发布？(one of: 周四 / 周五)」，预览、搜索、bot 读的时候用），另存问题（`group_messages.question`）：哪个座位的哪个审批、问了什么、状态（pending / answered / dismissed / closed）、每个问题的回答。
- **它不进任何待读**：系统消息分类里有一种 `bot.question`，归「不写投递记录」，所以不叫醒谁，不算谁的未读（包括你，群的提醒点靠「有审批在等你」显示），也不算进发言前检查的第 3 步（数的是投递记录）。bot 第一次在顶层发言前看最近 3 条（first touch）时，看的是这个地方的消息本身，问题也在里面，和别的不写投递记录的系统消息一样。bot 自己发言后读位置能不能跳过它，也和别的顶层系统消息一样不算。
- 你在群里回答（`pocket.groups.answer`）：交给 ChatService 的 `respond`，就是座位里那个审批的回答；审批已经不在了（这一轮结束了），问题记成 closed，告诉你它不再等了。在座位里回答也行，`permission.resolved` 让群里的问题跟着变。
- pocket-bots 重启时，审批随旧进程没了，还是 pending 的问题记成 closed。
- 其他审批、secret 的问题、登录还在座位里：群顶上「X needs your approval」只看这些（群里已经显示的问题不算），点一下进座位。座位里没有提议工具（`get_setup`、`propose_*`），改配置、建定时任务、存技能在 bot 自己的聊天里做。

## 团队

界面上用的是团队：你把一个任务交给团队，团队自己分工做完，leader 把结果交给你，你不用在群里指挥。每个任务开一个 session，session 就是一个有 leader 的群聊，上面的规则都照样适用。

**存了什么**：

| 存什么 | 说明 | 在哪 |
|---|---|---|
| 团队 | 名字、2–6 个成员、leader（必须是成员之一）、团队说明、工作目录、额外文件夹 | `bots.json` 的 `teams`（`TeamSchema`） |
| session 属于哪个团队 | 团队的 id；不属于团队的群是空的 | `groups.team_id`（迁移 21） |
| session 的团队说明 | 开 session 时团队说明的一份拷贝 | `groups.instructions`（迁移 21） |

**规则**：

- **开 session**：`pocket.teams.session` 按团队当时的样子建一个群：成员、leader、工作目录（可以只为这一次换，`cwd`）、额外文件夹、团队说明；名字取任务的开头（`sessionName`，最多 60 个字）。然后网页把任务作为第一条消息发进去（`pocket.groups.send`），和你在群里发消息一样，只叫醒 leader。成员里有归档或删掉的 bot 时不开，提示先改团队。
- **改团队只影响之后的 session**：session 建好就和团队分开，成员、leader、目录、说明都是开的时候那一份。改团队用 `pocket.teams.save`，同样检查成员（存在、没归档、2–6 个）、leader 在成员里（`teamProblem`）、目录存在。
- **团队说明进每个座位的 prompt**：座位的群聊 prompt 在角色那一段（leader 或成员的规则）后面加一段「The user's instructions for everyone in this team:」，内容是 session 存的说明（`seatGroup` 带出 `instructions`，交给 `groupPrompt`）。不属于团队的群没有这一段。
- **删除团队**（`pocket.teams.delete`）：它的 session 一起删掉，每个座位归档，bot 不受影响。
- **界面上不再有的**：新建群聊、改成员、唤醒方式和静音的入口都去掉了。没有 leader 的群（自由方式）和这些设置的代码还在，以前建的群照常能用，只是侧栏不列出。

**一个例子**：团队「Pocket dev」，Lena 是 leader（tech lead），成员 Dev（开发）、Ezra（explorer）、Quinn（QA），说明是「Run npm test after every change and say what you checked.」。

1. 你在团队页发「给 CLI 加一个 --version 参数，补上测试」：开了一个叫这个名字的 session，只有 Lena 被叫醒。
2. Lena 发 #2「@Dev 在 src/cli.ts 加 --version，读 package.json 的版本号；做完说明改了哪些文件、怎么验证的」。Dev 用一个新座位接这件活。
3. Dev 不知道参数在哪解析，在 #2 的线程里问「@Ezra 命令行参数是在哪个文件解析的？」：只叫醒 Ezra。Ezra 正在做自己的活 #3（Lena 派的「梳理配置加载」），它在做 #3 的座位里回答「@Dev src/args.ts 第 12 行」，不换座位，然后回去做 #3。这两条都不叫醒 Lena。
4. Dev 改完，跑了 `npm test`（30 个通过），在 #2 的线程里 @ Lena 汇报：改了 src/cli.ts、src/args.ts，`npm test` 30/30，`--version` 手动试过；没验证 Windows 上的路径。Lena 被叫醒。
5. Lena 不再跑一遍 `npm test`；它觉得要补一个 `--version` 的测试，派给 Quinn，说明测试已经全过、只缺这一个。Quinn 补完汇报后，Lena 回复你的任务：改了什么、验证了什么、没验证 Windows。

## bot 的群聊工具

| 工具 | 作用 |
|---|---|
| `group_send` | 发言：`thread` 发进某条消息的线程，`reply_to` 回复某条（回复线程里的消息就发在那个线程里），@ 别的 bot 就是交接，`files` 附上本机的文件（最多 6 个，必须有文字）。先过发言前的检查 |
| `group_send_draft` | 发出被搁置的草稿（再检查一次），`thread` 选哪个会话的，`discard` 丢掉，`anyway` 不再检查 |
| `group_read` | 读待读、读一个会话的未读、翻一页、定位读，见上面「读和搜索」 |
| `group_inbox` | 列出哪些地方有未读：几条、有几条 @ 它、最新是谁、读它的调用；`mentions` 只列 @ 它的。不读、不标已读 |
| `group_search` | 按词搜群消息，只给预览，不算看过 |
| `group_claim` | 认领任务（给消息号，不是任务的先变成任务），先认领的生效 |
| `group_task` | 改状态、建任务、把消息变成任务、指派（可带 `expected_revision`）、放下、改卡片（amend）、看卡片（show）、看历史（history）、删任务（只限自己建的）、列出任务（带 `rev=`） |
| `group_react` | 用表情回应一条消息，代替「收到」「好的」这类消息，不叫醒任何人 |
| `group_mute` | 静音或取消静音自己 |
| `group_follow` | 关注或取消关注一个线程（取消时带理由，记在线程里），`list` 列出关注的线程 |
| `group_reminder` | 给自己定提醒，挂在一条消息上；列出、推迟、改、取消、看记录。响的时候只叫醒自己 |
| `group_mention_delivery` | 查自己一条消息里每个被 @ 的成员：送到了、还在路上、丢了（为什么，该换人还是晚点再试），以及消息还送到了谁、没送到谁 |
| `group_members` | 成员、各自在不在忙、有没有静音、手上有哪些任务 |

工具列表每次请求都要带，所以说明只讲调用做什么，什么时候该用写在座位的 prompt 里。所有座位（leader、成员、没有 leader 的群）都不列出改配置的 `get_setup`、`propose_changes`、`propose_routine`、`propose_skill`，这些只在 bot 自己的聊天里有。有 leader 的群里，成员只列出 `group_send`、`group_send_draft`、`group_read`、`group_claim`、`group_react`、`group_members` 和 `search_chats`：它只做派给它的活，任务、提醒、关注、静音、@ 的去向、搜索群消息、问别的 bot、改配置都用不到。只是不列出，调用照样执行，因为会话只在开始时取一次工具列表，换 leader 之后已经开着的会话还是旧列表，下次开会话才换。

这些工具都在 pocket-bots 的 `bots` MCP 服务器上，所有 agent 都免审批。
