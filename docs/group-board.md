# 共享看板：群里 bot 的第三种协作方式

这篇讲共享看板为什么这样设计：它要解决什么问题，借鉴了哪几篇工作、哪里照搬、哪里改了，以及在 DeepSeek Harness 上和另外两种方式比的实验结果。怎么用见[使用指南](USAGE.md#群聊)，规则和例子见[群聊](group-chats.md#共享看板bot-之间不说话通过看板协作)，实现见[设计 §6.10](design.md#610-共享看板)。

## 1. 问题：自由度和开销

群聊原来有两种协作方式：

| 方式 | 谁和谁说话 | 好处 | 问题 |
|---|---|---|---|
| **自由** | 每条消息投给每个 bot，各自判断要不要说话 | 谁都能接任何活、互相补位 | bot 的每条消息叫醒其他所有 bot；一个 bot 说一句，N−1 个 bot 各花一轮去读、去判断。人越多，读的越多，来回越多 |
| **leader** | 只有 leader 收所有消息；成员只收派给自己的 | 叫醒少；按模型分工省额度 | 拓扑是一颗星：成员之间不能直接交接，所有结果都要经过 leader 读一遍；leader 卡住或出错，整个群都在等 |

这正是 ScaleMAS（下面 §2.1）指出的三个随人数增长的问题：每个 agent 要读的东西随群变大（自由方式）、有用的信息被淹没在质量不明的共享内容里、个别 agent 失败拖垮整个群（leader 方式）。

## 2. 借鉴了什么

### 2.1 ScaleMAS（arXiv:2610.16120，Meta FAIR 等，2026-10）

**做法**：把协作结构从 agent 身上搬到一个共享的「底座」（substrate）上。agent 之间不发消息，只和一个只追加的消息库打交道，三个操作：

1. **publish**：写一条消息（做了什么 `sub_task`、产出 `artifact`、依据 `rationale`、引用 `refs`），写入不叫醒任何人；
2. **search**：按内容搜，**最多返回 k 条**（k=8），排序 = 引用权重 + BM25 相关度（归一化到 [0,1]）；
3. **visit**：按地址取消息（最多 k 个）。

两条写入规则：引用必须存在；依据必须点名每条引用、说清它贡献了什么。引用权重：被后来的消息引用一次，权重向 1 走 α=0.3；每一步所有权重乘 γ=0.98。读出的消息**从不显示作者和权重**。

**关键结论**：每次读有上界，所以单个 agent 的阅读量不随群变大；被引用多的消息确实是正确答案依赖的那些（引用最多的五分之一里 85% 在正确答案的证据链上，最少的五分之一只有 29%）；去掉引用权重，BrowseComp-Plus 8 个 agent 从 60.0% 掉到 40.8%；一个 agent 永久失败时，群的表现和少一个 agent 差不多。

**我们照搬的**：bot 之间不发消息；四字段条目和两条写入规则；k=8 的有界搜索、BM25 + 引用权重排序、权重只重排相关条目；不显示作者和权重；条目在作者离开后还在（座位换新、bot 出错都不影响）；座位 prompt 里的四条规范（先读后写、边做边写中间结果、为被搜到而写、用了就引用）。

**改了的**（论文的设定和 pocket-bots 不一样）：

| 论文 | pocket-bots | 为什么 |
|---|---|---|
| N 个 agent 同时开始做同一个任务，直到各自交答案 | 开放的请求先给一个 bot，值得分时其他 bot 再加入（§3.2） | pocket-bots 的请求大小差别很大，「几个 test？」这种小事让 4 个 bot 都做一遍是纯浪费 |
| 每个 agent 各交一个答案，按 Pass@N 评分 | 最后一个做完的 bot 回复你一次（§3.3） | 你在群里要的是一个答案，不是 N 个 |
| 引用权重随「群的每一步」衰减 | 随「看板上每写一条」衰减 | pocket-bots 没有全局步数；用条目数当时钟，排序只取决于看板内容，每次搜索时重算，不存 |
| 消息库为一个任务而建，任务结束就丢 | 看板跟着群，一直保留（满 5,000 条后拒绝再写） | 群是长期的，后来的请求能搜到之前做过的事 |
| 资源引用（语料片段、仓库文件） | 引用只有看板条目（B3）和群消息（#12） | 文件路径没法在写入时可靠地验证「存在」，写进结果里即可 |
| 浮点 BM25 | 同样是浮点（dsh-ATN 用整数实现，为了逐字节重放审计） | 我们不需要审计重放；排序对同样的输入是确定的 |

### 2.2 Park et al.，Scaling Discovery through Test-Time Communication（arXiv:2609.21032，2026-09）

**做法**：k 个相同的 agent 在同一个容器里，通过共享目录通信：只追加的通信日志、发现、反证、分数日志；没有角色和中心。唯一由协议强制的分配是**槽位**：agent 用原子的 `mkdir` 抢编号槽位，抢到后声明一个和别人不同的做法。

**关键结论**：在有可靠验证信号（关卡通过、分数）、算力足够时，team@k 明显好于 best@k（ARC-AGI-3 上 team@5 抵得上 33 个独立 agent）；但**算力少时有「协调税」**，独立 agent 更好（每个 agent 输出 ≤40 万 token 时 best@k 领先）；没有密集验证信号的 Terminal-Bench 上 team@2 不如 pass@2；agent 容易「扎堆」，相互沟通后变成少数几组在做重复的事。

**我们拿来的**：

- **认领先到先得**（对应槽位）：条目可以带 `claim`，同一轮里同一块只能被认领一次，和写入在同一个事务里检查。论文的槽位是编号，天然不会撞；我们的认领是 bot 自己起的名字，第一批实验里两个 bot 用不同的写法认领了同一个文件，所以「同一块」按重叠判断：名字相同、有一个文件相同、或一个认领的词都在另一个里（`claimsOverlap`）。论文里抢槽位是防扎堆的关键；我们原本只在提示里建议「从第几块开始」，看了这篇后改成强制的。
- **带着验证写结果、公开纠错**（对应「verified progress sharing」和反证日志）：prompt 要求结果写明怎么验证的（跑了什么、结果如何）、没验证的标出来；只在证据成立时在别人的结果上继续；发现条目错了就写一条引用它的纠正。
- **协调税**：小请求不该付协调的代价，这是「先给一个 bot」的另一条理由。

**没拿的**（他们的核心是「验证过的进展共享」：几个 agent 攻同一个难题，用验证器判断谁的突破更好，在彼此的突破上继续，同时刻意保持做法不同。我们做的是分工，这一核心没有拿）：

- **「时间没到不停」「一直在行动」**：他们做的是有时限的开放式优化；pocket-bots 的请求做完就该停，多跑就是多花钱。
- **强制多样化**（做法必须不同、高门槛才跟进、卡住换思路）：为有验证器的搜索设计，多样化抬高最好的那个；分工的活里重复就是浪费。以后要支持「把某个指标做到最好」这类请求时再考虑。
- **分数日志 / 排行榜**：需要可以反复查询的分数，一般请求没有。
- **agent 自己写协调约定**：开放、费 token；最主要的撞车已经由认领管住。
- **同步屏障、文件锁**：同步屏障是 ARC 游戏专用的；pocket-bots 管不了 CLI 写文件，认领对文件只是约定，不是强制。

### 2.3 dsh-ATN（github.com/ff66ccff/dsh-ATN，DeepSeek Harness 插件）

**做法**：「自适应拓扑网络」：节点有出边上限 min(8, ⌈log₂N⌉+1)，可以按协作反馈自己换边（`atn_status(rewire=…)`），通信复杂度 O(N log N)；孤儿任务可以被空闲节点原子认领；遥测捎带在正常输入里，不额外叫醒。0.6 版又把 ScaleMAS 的 substrate 接了进来（`atn_publish`、`atn_search`、`atn_visit`）：整数 BM25、CJK 二元分词、准入失败原子回滚、发布不叫醒任何人。

**关键结论**：作者用 deepseek-v4.1-flash 做了 11 轮等预算对照，**没有测出自适应拓扑的独立收益**：终轮 5 臂各 14 个 seed，原生 Team 14/14、自适应拓扑 10/14、单 agent 9/14，所有差异都不显著；项目随后把定位从「协作涌现」转向「数据边界」。substrate 只做了零模型的结构验证，不主张任何收益。

**我们拿来的**：

- **不做拓扑**：既然动态换边在同一个模型上没测出好处，我们不让 bot 选择和谁连接，也不按相关度把消息路由给部分 bot。
- **中文分词**：CJK 连续段切成相邻两字的词（`boardTokens`），中文请求和条目才能互相搜到。照搬时也带上了它的缺陷：中文和英文、数字之间不加空格时（「缓存TTL为5分钟」）整段成了一个词，搜 TTL 一条也找不到；后来改成把中文和紧挨着的字母数字分开（§5）。
- **孤儿任务接手**：bot 的一轮失败了，它在这一轮里的认领被释放，别人可以重新认领，回答的 bot 会被告知这些块（§3.3）。
- **原子的写入**：规则检查、认领、编号在同一个事务里，被拒的条目不占编号、不改任何状态。
- **发布不叫醒任何人**、读取只花读的那个 bot 自己的一步。
- **诚实地比**：同一个模型、同样的任务和 seed，报告成本和结果，不把论文的数字当成我们的结论（§4）。

**没拿的**：

- **自适应拓扑**（换边、出边上限、按反馈选邻居）：它自己的数据说明没有收益。
- **保管层 / 数据边界**：pocket-bots 是一个人的本地 bot，没有多租户的数据隔离需求。
- **整数 BM25 和逐字节重放审计**：为审计设计；我们的引用权重每次从条目重算，不需要重放。
- **评价、步数预算、派生节点**：群成员是固定的，额度由各个 CLI 自己管；评价本质上是声誉机制，dsh-ATN 后来也把「不再加声誉算法」列为禁区。
- **捎带通知**：没有拓扑，就没有要通知的邻居变化。

### 2.4 pocket-bots 自己之前的尝试（PR #27 里的 working board）

PR #27 曾经给群加过一块类似 ScaleMAS 的看板（不可变、带引用的条目，有界的搜索和读取，不叫醒任何人），但**保留了原来的消息和叫醒规则**：bot 既在群里说话，又写看板。同 seed 的 Contradiction Audit 对照里，加看板那一组在每个成本指标上都更差（轮数 21 对 12、叫醒 16 对 11、群消息 208 KB 对 135 KB、用时 429 秒对 246 秒），找到的矛盾一样多（20/20），于是被删掉了。

教训是：**看板要替代消息，而不是加在消息旁边**。ScaleMAS 的收益来自「agent 之间没有推送」，只多一个渠道只会多一份工作。所以这次的共享看板是一种独立的方式：bot 的消息到不了别的 bot（§3.1），看板是 bot 之间唯一的渠道。

## 3. 设计

### 3.1 bot 之间不发消息

看板群里，bot 发的消息只投给你和它自己；@ 别的 bot 也叫不醒它。这去掉了自由方式里最贵的部分：一个 bot 说一句，其他 bot 各花一轮。bot 想让别人知道什么，就写条目；想知道别人做了什么，就搜。写和读都是它自己当时的一步，不打断别人。

### 3.2 一轮：先给一个 bot，值得分再扩开

你的一条请求叫醒了 bot，就开始**一轮**。开放的请求（没 @ 谁）先只给**一个** bot（空闲的优先，其次是最久没当第一个的）；其他 bot 等着，只在两种情况下加入：

1. 第一个 bot 在这一轮里认领了一块：它把计划写到看板上、认领自己那块，说明它把活拆开了（只写条目不算：ScaleMAS 要 bot 边做边写，单干的 bot 也会写）；
2. 它这一轮失败了，还没有回答：别人接手。

它做得久不算。第一版有「一分钟后还在做就让别人加入」，第二版改成三分钟，实验里两次都有害：第一个 bot 正在独自把活做完，计时一到，加入的 bot 只是重复验证（§4.3）。第一个 bot 在别人加入前做完，别人就不被叫醒。这样小请求只花一个 bot 的钱；要不要拆，由看过请求的那个 bot 决定。你 @ 了几个 bot，它们就同时开始。

拆的时候按输入拆（文件、文档、章节），不按检查项拆：审计任务按事实类型拆成 8 块时，每块都要把 72 篇文档重读一遍。

加入的 bot 按顺序编号，提示里列出已经被认领的块，建议从第几块开始；它在这一轮里的第一条条目必须带认领，否则拒绝（实验里 bot 常在文字里写「我认领了」却没带 `claim`，锁就没生效）。真正防止撞车的是认领（§2.2）。

### 3.3 最后一个做完的回答

每个 bot 做完自己那块就停（调用 `board_finish`，或者它的一轮结束），不在群里发进度。最后一个做完的回答你：它调用 `board_finish` 时工具结果直接告诉它；它是一轮结束才算做完的，就单独叫醒它回答。所以一个请求通常只有一条回答，而且是在看过看板之后写的，包含所有人的结果。

这一步是 pocket-bots 自己确定性地做的（谁还在做、谁最后做完都记在库里），不靠 bot 之间商量，也没有一个固定的 leader：谁回答取决于谁最后做完。

有 bot 的一轮失败了，它在这一轮里的认领被释放（dsh-ATN 的孤儿任务接手）：别的 bot 可以重新认领；回答的 bot 收到的提示里列出这些块，让它去看板上查做到哪了，能补就补，补不了就在回答里说明。

### 3.4 和另外两种方式的对比

| | 自由 | leader | 共享看板 |
|---|---|---|---|
| bot 的消息叫醒谁 | 所有 bot | 只有被派活的或 leader | 谁都不叫醒 |
| 你的开放请求叫醒谁 | 所有 bot | leader | 一个 bot；值得分时再叫其他 bot |
| 谁决定分工 | 各自认领任务 | leader | 看板上先到先得的认领 |
| 一个 bot 要读多少 | 群里所有消息 | 成员只读派给它的；leader 读所有汇报 | 每次搜索最多 8 条 |
| 一个 bot 出错 | 别人可能补上 | 成员出错要 leader 处理；leader 出错整个群停 | 别人照常做完，最后一个回答 |
| 谁回答你 | 谁先说谁算 | leader | 最后一个做完的 |
| 座位每次请求带的群聊 prompt / 工具说明 | 约 6.8K / 11.6K 字符 | leader 8.6K / 11.6K；成员 4.3K / 4.6K | 约 5.3K / 6.3K |

## 4. 实验

### 4.1 怎么比

- **bot**：4 个一样的 bot（Ada、Ben、Cy、Dee），DeepSeek Harness，模型 `sophon/DeepSeek-V4.1-Flash-1017`，审批模式 workspace-write，同一个工作目录。
- **三种方式**：自由（Everyone 唤醒）、leader（Ada 当 leader）、共享看板（第二版：第一个 bot 认领时别人加入，或者三分钟后加入；认领按重叠判断）。
- **三个任务**（都在 pocket-bots 仓库外，跑实验的脚本也在仓库外）：

  | 任务 | 内容 | 怎么打分 |
  |---|---|---|
  | 快问题 | 「test/semver.test.js 里有几个 test？只回数字」 | 第一条 bot 消息是不是 8 |
  | 编码 | 一个小 JS 库，4 个模块（slugify、duration、semver、wrap）都是空实现，共 30 个测试；参考实现 30/30 | 跑完后的通过数，测试文件有没有被改 |
  | 审计 | 72 篇虚构平台的文档，12 个服务 × 8 种事实，埋了 10 处矛盾 | 群里 bot 的消息提到了几个被改的文件 |

- **每个任务、每种方式跑 3 次**，同一次的三种方式同时开跑。
- **成本**：从 DeepSeek Harness 的会话日志里，把所有座位每次模型调用的输入、输出 token 加起来。DSH 不单独报告缓存命中，输入里包含被缓存的前缀，所以数字比实际账单高，三种方式都一样高估。
- **时间**：从你发请求，到所有座位都空闲。

### 4.2 结果（2026-10-26，第二版）

正确率三种方式都是满分：快问题 3/3 答对、编码 30/30、审计 10/10。所以只能比成本和时间：

| 任务 | 自由 | leader | 共享看板 |
|---|---|---|---|
| 快问题：token（3 次） | 447K（399K / 500K / 441K） | **80K**（78K / 82K / 78K） | 94K（82K / 67K / 134K） |
| 快问题：用时 | 38 秒 | **23 秒** | 31 秒 |
| 编码：token | **0.99M**（0.84M / 1.08M / 1.04M） | 1.19M（1.29M / 1.30M / 0.98M） | 1.29M（0.91M / 1.29M / 1.66M） |
| 编码：用时 | 269 秒 | **262 秒** | 338 秒 |
| 审计：token | 3.40M（3.27M / 3.53M / 3.39M） | 6.38M（3.17M / **11.08M** / 4.88M） | **3.21M**（4.76M / 2.06M / 2.82M） |
| 审计：用时 | **473 秒** | 929 秒 | 602 秒 |

**结论：第二版的共享看板没有稳定的优势。** 它比自由方式省的只有快问题（-79%），而那来自「先只给一个 bot」，leader 方式本来就只叫醒一个；编码任务它最贵也最慢；审计按中位数最便宜（2.82M，自由 3.39M、leader 4.88M），但三次之间差两倍多。

第一版（只跑了 1 次，加入的计时是一分钟，认领只比相等）：编码看板 1.46M、自由 0.69M、leader 1.27M；审计看板 2.78M、自由 5.27M、leader 2.67M（那次 leader 被服务中断打断，没给出最后的回答）。

### 4.3 为什么

看每次运行的过程：

- **快问题**：看板和 leader 一样只用了一个 bot；自由方式下四个 bot 都被叫醒、都去读，答的只有一个。
- **编码**：三次里第一个 bot 都选择了自己做，一次都没主动拆。但它做了超过三分钟，计时一到，另外三个 bot 被叫进来；第三次运行里，三个加入的 bot 的条目全是「我已验证 slugify 的测试都通过」，每个花了 19 万到 63 万 token。第三版去掉了这个计时（§3.2）。
- **审计**：第一次运行花了 4.76M，按事实类型拆成 8 块，每块都要重读全部文档；而且有 bot 在文字里写「我认领第 4 块」却没带 `claim`，两个 bot 审了同一块。第三版要求加入的 bot 第一条先认领，并提示按输入拆。
- **leader 的波动**：审计第二次，三个成员交回结果后，leader 又派了一轮「核对」：让每个成员把另一个成员那份完全重做一遍，成员的活翻了一倍；leader 自己读了所有汇报，6 轮里上下文涨到 109K token，花了 5.3M。整次 11M、18 分钟。成员结果的读者只有 leader 一个，它的上下文随群变大，这正是 ScaleMAS 说的第一个问题。
- **正确率全是满分**：这三个任务对一个 Flash bot 来说都不难，审计语料（约 6K token）一个 bot 就能读完，测不出跨 bot 拼合信息的好处；也没有注入失败，测不出容错。

### 4.4 第三版复测（2026-10-26）

同样的任务、三种方式各 3 次，看板换成第三版：去掉计时（别人只在第一个 bot 认领或失败时加入）、加入后先认领、失败释放认领、提示按输入拆。自由和 leader 的规则没变，也一起重跑，三种方式同时开跑。

| 任务 | 方式 | 第二版 token（均值 / 中位数） | 第三版 token（均值 / 中位数） | 第二版用时 | 第三版用时 | 第三版正确率 |
|---|---|---|---|---|---|---|
| 快问题 | 自由 | 0.45M / 0.44M | 0.44M / 0.44M | 38 秒 | 34 秒 | 3/3 |
| 快问题 | leader | 0.08M / 0.08M | 0.08M / 0.08M | 23 秒 | 25 秒 | 3/3 |
| 快问题 | 看板 | 0.09M / 0.08M | **0.08M / 0.07M** | 31 秒 | 26 秒 | 3/3 |
| 编码 | 自由 | 0.99M / 1.04M | 1.07M / 0.91M | 269 秒 | 230 秒 | 30/30 |
| 编码 | leader | 1.19M / 1.29M | 1.73M / 1.39M | 262 秒 | 316 秒 | 30/30 |
| 编码 | 看板 | 1.29M / 1.29M | **0.20M / 0.21M** | 338 秒 | **170 秒** | 30/30 |
| 审计 | 自由 | 3.39M / 3.39M | 4.07M / 3.66M | 473 秒 | 410 秒 | 10/10 |

| 审计 | 看板 | 3.21M / 2.82M | **0.61M / 0.55M** | 602 秒 | **334 秒** | 10/10 |

第三版的看板在三个任务上都最省、最快，正确率不变：编码比自由方式省 81%、比 leader 省 88%，审计省 85% 和 92%。

**但原因要说清楚：九次运行里，第一个 bot 每次都选择自己做完，一次都没拆，别的 bot 从没被叫醒，看板上一条条目都没有。** 第三版的看板在这些任务上等于「只用一个 bot」。省下来的是多 bot 协作的全部开销，而不是看板上的协作带来的收益；看板机制本身（搜索、引用、认领）这一轮完全没被用到。第二版之所以贵，是那个计时器把一个 bot 能做完的活硬拆给了四个。

**leader 的问题在这一轮更明显**：
- 审计第二次：leader 安排三人分页抽取、一人合并，再派两个人「独立核对」；之后 leader 连着三次遇到 DeepSeek Harness 的「session is closing」运行时错误被停下，最终没有回复你，25 分钟超时（得分 10/10 来自成员的合并报告）。
- 审计第三次：leader 安排两轮完整的独立审计，再加一轮裁决，一个成员就花了 5.8M token，也超时了。
- 编码第三次：leader 审核时给了一个错的期望，又让成员改回来，自己 7 轮花了 1.46M。

在这个模型上，leader 倾向于安排重复验证，成本和用时的波动都最大。

**自由方式**照旧：每次四个 bot 都被叫醒，认领只让一个 bot 动手改，但别的 bot 读完之后常常再「独立核对」一遍（审计第一次，一个没认领到的 bot 照样把 72 篇文档全读了一遍，花了 1.3M），成本是单个 bot 的 5 到 7 倍。


## 5. 中文分词

看板的搜索要能处理中文。我们比较了几种分词，在同一个手写的中文测试集上。

### 5.1 怎么比

- **测试集**：75 条中文看板条目（「我已…」加结果，夹着英文和代码名），60 个查询，每个查询人工标出相关条目。条目里特意放了容易误配的：「库存」和「数据库存储」，「单价」和「下单价格」，「长江」和「长江大桥」，「验证」和「验证码」，「发布」和「发布会」。
- **查询分 8 类**：精确词 8、新词和领域词 10（白屏、灰度、熔断、幂等…）、粒度不一致 14（查询是长词的一部分，或者比原文的词长）、歧义和跨词误配 8、中英混合 7、中英文不加空格 5、问句 5、近义改写 3（「页面空白」和「白屏」，作对照：关键词方法都不擅长）。
- **比较的分词**：我们的（修复前和修复后）、只要二元加单字、jieba 精确模式和搜索模式（`@node-rs/jieba`）、二元加 jieba、zvec 的 jieba（zvec-grep 用的配置）、ngram 2、standard（中文切成单字）。打分有两套：我们的 BM25 和 zvec 的 BM25，同一套分词交给两边打分，结果几乎一样（nDCG 相差不超过 0.01），所以差别来自分词。
- **指标**：前 8 条（看板每次返回 8 条）的召回率、MRR、nDCG，以及一条相关都没找到、第一名不相关的查询数。

### 5.3 发现

- **新词、领域词大家都没问题**：jieba 的 HMM 能认出新词，二元不需要词典。
- **jieba 的弱点：查询是词典里某个长词的一部分**。「长江大桥」「监测数据」在词典里是整词，搜「长江」「大桥」「监测」一条都找不到；「启动慢」搜不到「冷启动」。搜索模式和 zvec 的 jieba 能找回这些，但「登录页面」对「登录页」所有 jieba 都不行（切成「登录/页面」和「登录/页」，只剩「登录」对得上）。
- **二元的弱点：同字不同词**。搜「验证」时含「验证码」的条目排在前面（nDCG 0.55，jieba 精确 1.00）；搜「发布」时「发布会」排第一。但它从不一条都找不到。
- **修复前的缺陷**：中文和英文、数字紧挨着时整段成了一个词，「中英无空格」这一类只有 0.82，搜 TTL、Redis、npm test、CI 都找不到。修复后 0.98。修复前两个字的中文段还会被算两次（「白屏」输出「白屏 白屏」），修复后只算一次。
- **二元 + jieba** 能修好歧义（「验证」0.55 → 0.97），但近义改写变差，总分持平，而且要加一个原生依赖。

**决定**：保留二元切分（不用词典、不加依赖），修好中英文分开和重复计数；不换成 jieba，也不加二元加 jieba。将来要是为了向量搜索接入 zvec，全文这一路用它的 ngram（n=2），效果和现在一致。

**局限**：测试集是手写的，各分词之间的差别集中在大约 8 个查询上，不算统计显著；真实 bot 写的条目更长、中英文混得更多。几个关键用例写进了 `tests/group-board.test.ts`。

## 6. 结论和下一步

- **在这三个任务上，最省最快的是只让一个 bot 做**：第三版的看板正是这样做的（第一个 bot 自己决定不拆），成本是自由方式的 1/5 到 1/7、leader 的 1/8 到 1/13，正确率一样。对 DeepSeek-V4.1-Flash 来说，这些任务都没大到值得拆；拆开只会多付协调的开销（Park et al. 的「协调税」）。
- **真正被验证有用的机制是「开放请求先只给一个 bot，它决定要不要拆」**。它不依赖看板本身：可以单独移植到自由方式，解决「一条消息叫醒所有 bot」；leader 方式也可以允许 leader 判断「这件我自己做」，而不是一律派活。
- **看板上的协作（搜索、引用、认领、跨 bot 拼合信息）还没有被检验过**：第二版用过但被计时器带偏，第三版一次也没用上。要检验它，需要一个一个 bot 确实做不完、或者明显做得慢、各块之间又要互通信息的任务。
- **leader 方式在这个模型上的风险是过度验证**：自己安排多轮重复核对，成本和用时波动很大，leader 一出错整件事就没有回答。
- **下一步**：
  - 用短剧剧本拆解做能拉开差距的测试（几十集中文剧本，埋好角色别名、服装变化和跨集连续性错误，按 Jellyfish 的格式输出），比较五种：单个 bot、自由、leader、看板，以及「leader 管流程、产出和角色设定放共享存储」的组合方式，再加一组中途让 leader 失败；
  - 不管看板最后留不留，把「先只给一个 bot」移植到自由方式。
- **按数据决定去留**：在真正需要协作的任务上，如果看板的协作打不过 leader 和单个 bot，就不保留看板的协作部分。
